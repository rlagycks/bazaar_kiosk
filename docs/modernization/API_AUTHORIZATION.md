# 단계 3 — API 역할 인가와 CSRF 경계

2026-09-13 · [이슈 #55](https://github.com/rlagycks/bazaar_kiosk/issues/55) ·
[BK-R001](ANALYSIS_REPORT.md#bk-r001)(Critical) · 단계 [3](BLUEPRINT.md#phase-3) ·
결정 [D-036](DECISIONS.md)·[D-040](DECISIONS.md).
선행 측정은 [권한 현황](AUTHORIZATION_MATRIX.md)이다.

## 무엇을 고쳤는가

측정 결과 `orders/views/api.py`는 세션이나 역할을 한 번도 읽지 않았다. API 경로 9개가
익명 포함 모든 행위자에게 열려 있었고, 쓰기 3개는 CSRF를 강제하는 클라이언트에서도
토큰 없이 통과했다. 화면은 `@require_roles`로 막혀 있었지만 그 뒤의 API가 열려 있어
화면 단위 권한은 실효가 없었다. D-031로 외부 접속이 확정된 상태에서 이는
인터넷에서 익명으로 주문을 만들고 취소할 수 있다는 뜻이다.

## 적용한 매트릭스

| 엔드포인트 | 허용 주체 | 근거 |
| --- | --- | --- |
| `order-status` (상태 변경·취소) | 주방 | D-040 개정 |
| `order-item-progress` (조리 진행) | 주방 | D-040 |
| `stats-dashboard`·`stats-menu-counts` (매출) | 주방 카운터 | D-040 |
| `tables`·`menus`·`orders-collection`(GET/POST)·`order-detail`·`kitchen-menu-summary` | 인증된 계정 전체 | D-036의 익명 차단만 적용 |

마지막 행은 의도적으로 역할을 제한하지 않았다. D-040이 이 엔드포인트들의 주체를
정하지 않았으므로, 추측으로 역할을 넣으면 받지 않은 승인을 만드는 것이 된다.
익명 차단은 D-036이 실제로 결정한 부분이라 전 구간에 적용했다.

주방 계정은 D-034로 1개로 단일화하기로 했으나 아직 구현 전이다. 세 역할이 오늘도
같은 주방 화면과 같은 기능을 공유하므로 `KITCHEN_ROLES`는 셋 전부를 뜻한다.
단일화는 4A2의 인증 전환에서 함께 처리한다.

## 구현

[전용 데코레이터](../../orders/views/auth.py)의 `require_api_roles()`를 사용한다.
화면은 로그인 화면으로 리다이렉트하지만 API는 그럴 수 없다. 호출자가 JSON을 파싱하는데
리다이렉트는 HTML 로그인 페이지로 도착해서, 브라우저에는 권한 문제가 아니라
파싱 오류로 나타난다. 그래서 API 거부는 JSON `403`이다.

**인가는 `cache_page` 바깥에 둔다.** 안쪽에 두면 인가된 호출자가 채운 캐시 본문이
그 뒤 누구에게나 제공된다. `tables`·`menus`가 해당하며 회귀로 고정했다.

**메서드 검사보다 인가가 먼저 실행된다.** 미인증 호출자가 어떤 메서드를 받는
경로인지 알아낼 필요가 없다. 인증된 호출자에게는 405 경계가 그대로 남는다.

세션 없음과 역할 불일치를 모두 403으로 답한다. 401과 403을 나누는 것은
D-035의 토큰 갱신 흐름이 있어야 의미가 생기므로 4A2로 넘긴다(D-036 미결).
거부 본문에는 호출자의 역할도 허용 목록도 넣지 않는다. 거부된 클라이언트에게
쓸모가 없고 권한 모델을 그려주는 정보다.

## CSRF

쓰기 3개의 `@csrf_exempt`를 제거했다. 코드 주석도 `개발 편의. 운영 전 제거 권장.`이었다.

프런트엔드는 이미 준비돼 있었다. `order.html`의 주문 생성과
`kitchen_supervisor.html`의 취소·조리 진행이 모두 `X-CSRFToken` 헤더를 보낸다.
다만 그 토큰은 `csrftoken` 쿠키에서 읽으므로 쿠키가 반드시 있어야 한다.
로그인 페이지의 `{% csrf_token %}`이 쿠키를 설정하지만, 로그인과 첫 쓰기 사이에
쿠키가 지워지거나 회전하면 화면이 조용히 깨진다. 그래서 쓰기 기능이 있는 화면 4개에
`@ensure_csrf_cookie`를 붙였다. `b1_counter.html`은 읽기 전용이라 대상이 아니다.

`serve.html`과 `role_select.html`은 어느 뷰도 렌더하지 않는 미사용 템플릿이라 건드리지 않았다.

## 검증

[권한 회귀 13개](../../orders/tests/test_permissions.py). 준비 단계의 특성화 테스트를
교체한 것이다. **교체 전에 이전 `OPEN` 기대값이 실제로 실패하는지 확인했다**(43개 단언).
그 확인 없이는 통과하는 suite가 아무것도 증명하지 않는다.

행위자 7종(익명·역할5개·서버가 발급한 적 없는 역할을 담은 GHOST 세션)과
경로·메서드 쌍 10개의 조합을 전수 검사한다. 경로는 9개이고 `orders-collection`이
GET과 POST를 모두 받으므로 검사 단위는 10개다. 허용되는 조합은 403이 아님이 아니라
**200/201 성공**을 단언한다. 그러지 않으면 핸들러를 망가뜨린 가드도 통과로 보인다.

전용 Compose에서 전체 59개(migration 15 · 앱/guard 44), skip 0.

독립 리뷰가 위 8개로는 잡히지 않는 종류를 찾아냈다. 회귀를 보강하고 다시 확인했다.

| `endpoints()` 키 중복으로 행 1개 소멸 | 1 | dict 리터럴은 중복 키를 조용히 버린다 |
| 거부 본문에 **한국어로** 역할·허용집합 노출 | 1 | 단언이 영문 코드만 찾았다. 앱은 한국어로 말한다 |

**첫 8개가 데코레이터 호출부만 건드렸다는 것이 문제였다.** 허용 역할 상수 자체를 넓히면
테스트의 기대값이 같이 움직여 통과했다. 이제 승인된 매트릭스를 테스트에 **리터럴로** 적고
상수는 `test_the_role_constants_still_match_the_approved_matrix`가 따로 대조한다.
엔드포인트 표는 `orders/urls.py`의 API 경로 집합과 대조하고 개수도 고정한다.
`require_api_roles()`는 역할 이름을 받았는데 집합이 비거나 모르는 이름이 섞이면
import 시점에 `ValueError`로 멈춘다.

기존 여정 테스트는 인가 적용 전후 모두 통과했다. baseline·dashboard 회귀가
이미 올바른 역할로 로그인하고 있었기 때문이며, 이것이 "정상 기존 여정 유지" 근거다.

## 남는 경계

이것은 **인가**다. 인증 방식은 바꾸지 않았다. 여전히 역할 선택 + 공용 PIN 세션이며
D-035의 id/password + JWT 전환은 4A2다. 따라서 자격증명 자체의 약점(BK-R002)은 남는다.

### 리뷰가 지적한 미해결 노출 — 매출 기밀성은 아직 달성되지 않았다

**`stats-dashboard`를 주방 카운터로 제한했지만 같은 숫자가 `orders-collection` GET으로 새어 나간다.**
`_serialize_order`는 주문마다 `total_price`·`payment_method`·`received_cash_amount`·
`received_ticket_amount`·`change_amount`를, 항목마다 `unit_price`·`line_total`을 담는다.
이 엔드포인트는 인증만 요구하므로 ORDER 계정이 최대200건을 받아 매출과 현금/식권 구성을 재구성할 수 있다.
`order-detail`도 임의 id로 같은 내용을 준다.

즉 **BK-R001의 매출 기밀성 항목은 이 변경으로 달성되지 않았다.** 익명 차단과 쓰기 제한은 달성됐다.
D-040이 이 두 엔드포인트의 주체를 정하지 않아 추측으로 좁히지 않았는데, 이 경우 "정하지 않음"은
중립이 아니라 이미 내린 제한을 무효로 만든다. **D-040 후속 결정이 필요하다.**

401/403 구분, 주문 생성·조회 엔드포인트의 주체, 주방 계정 단일화, 토큰 수명·회수,
다중 기기 경합은 모두 미결이다. Django 관리자(`/admin/`) 권한은 D-011이다.

### 리뷰가 지적한 인증 측 약점 — 이 단계의 범위 밖이나 지금 더 중요해졌다

세션이 이제 9개 API의 **유일한 인가 자격증명**이다. 그래서 아래가 전보다 무겁다.

- **세션 고정:** `login_view`가 역할을 넣기 전에 `cycle_key()`를 부르지 않는다. 로그인 전에 심어둔
  세션 키가 로그인 후에도 그대로 유효하다. 한 줄이면 닫히지만 인증 코드 변경이라 별도 승인 사안이다.
- **거부 응답이 항상 JSON은 아니다.** `CsrfViewMiddleware`가 데코레이터보다 바깥이라
  토큰 없는 쓰기는 이 가드에 닿기 전에 **HTML 403**으로 거부된다. 404도 HTML이고
  `DEBUG` 기본값이 켜짐이라 디버그 페이지가 그대로 나온다.
- **역할 회수가 세션에 닿지 않는다.** 유효성 검사가 `ROLE_TO_URLNAME`(화면 지도)을 보고
  실제 자격증명 저장소인 `settings.ROLE_PINS`를 보지 않는다. 환경에서 역할을 지워도
  이미 발급된 세션은 계속 통과한다.
- **로그아웃이 CSRF 가능한 GET이다.** `<img src=".../logout/">` 한 줄로 세션이 날아간다.
- 4자리 PIN에 시도 제한이 없고 기본값이 저장소에 있다(BK-R002). 이 단계의 모든 통제가 그 아래에 있다.

브라우저 실제 여정은 검증하지 않았다. 서버 응답만 테스트했으므로
화면이 로그인 전에 호출하는 경로가 남아 있는지는 4B1의 브라우저 검사에서 확인한다.

BK-R001은 저장소에서 원인을 제거하고 회귀로 고정했으므로 증거 상태는 `Repo-fixed`가 되지만
**해결 상태는 운영 인수 전까지 Open이다.** 외부 노출·실제 자격증명·배포는 미실행이다.
schema·migration·번호/결제 계약·UI는 변경하지 않았다.
