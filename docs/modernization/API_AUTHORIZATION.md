## 무엇을 고쳤는가

측정 결과 `orders/views/api.py`는 세션이나 역할을 한 번도 읽지 않았다. 당시 API 경로 9개가
익명 포함 모든 행위자에게 열려 있었고, 쓰기 3개는 CSRF를 강제하는 클라이언트에서도
토큰 없이 통과했다. 화면은 `@require_roles`로 막혀 있었지만 그 뒤의 API가 열려 있어
화면 단위 권한은 실효가 없었다. D-031로 외부 접속이 확정된 상태에서 이는
인터넷에서 익명으로 주문을 만들고 취소할 수 있다는 뜻이다.

**주문 조회는 처음에 인증만 요구했다가 리뷰 후 좁혔다.** 첫 판단은 "D-040이 주체를
정하지 않았으니 추측으로 좁히지 않는다"였는데 여기서는 틀렸다. 직렬화된 주문 본문이
`total_price`·`payment_method`·현금/식권 구성·거스름돈·항목별 단가를 담으므로,
조회를 열어 두면 `stats-dashboard`를 카운터 전용으로 막은 것이 무효가 된다.
**주체 미정이 중립인 경우와 이미 내린 제한을 무효로 만드는 경우는 다르다.**

생성 POST는 그대로 전 계정이다. 주문 화면은 생성만 하고 읽어오지 않는다.
따라서 `orders-collection`은 메서드별로 주체가 다른 첫 엔드포인트이며
`require_api_roles(by_method=...)`가 그것을 표현한다.

마지막 행은 여전히 역할을 제한하지 않는다. 금액을 담지 않아 위와 같은 무효화가
일어나지 않고, D-040이 주체를 정하지 않았으므로 추측으로 넣으면 받지 않은 승인을 만든다.
익명 차단은 D-036이 실제로 결정한 부분이라 전 구간에 적용했다.

2026-09-15에 D-034 단일화를 구현했다. 현재 역할은 `ORDER`·`B1_COUNTER`·`KITCHEN`이고
`KITCHEN_ROLES`는 `KITCHEN` 하나다. 주방 전체·홀·포장 URL과 필터는 유지하며
세 화면 모두 주방 역할로 접근한다. 삭제된 두 역할은 로그인과 기존 세션에서 거부하고
자동 변환하지 않는다. 기존 `ROLE_PINS`에서 해당 항목을 제거하고 재시작한 뒤 재로그인한다.
PIN 세션은 유지하며 id/password + JWT 전환은 다음 독립 작업이다.

## 구현

[전용 데코레이터](../../orders/views/guards.py)의 `require_api_roles()`를 사용한다.
4A2 착수 시점에 두 가지가 바뀌었다. 로그아웃은 POST 전용이 됐고,
세션의 역할 유효성은 정적 표가 아니라 `orders.roles.provisioned_roles()`를
요청마다 읽어서 판정한다. 그래서 자격증명을 회수하면 이미 열려 있던 세션도 거부된다.
**재시작은 여전히 필요하다.** `ROLE_PINS`는 import 시점에 환경에서 읽으므로 실행 중에는 바뀌지 않는다.
이 변경이 바꾸는 것은 "재시작이 필요한가"가 아니라 "재시작이 누구를 끊는가"다.
항목을 지우고 재시작하면 그 역할만 끊기고, 예전에 유일한 수단이던 `SECRET_KEY` 교체는 전원을 끊었다.
**회수뿐이고 교체는 아니다.** PIN 값만 바꾸면 옛 PIN 으로 연 세션은 살아 있다.

이 가드는 4A2 착수 시점에 `auth.py`에서 `guards.py`로 옮겼다. 신원을 증명하는 흐름과
증명된 호출자가 무엇을 할 수 있는지를 분리하기 위해서다. 동작은 바꾸지 않았다.
역할 이름 자체는 `orders/roles.py`에 있다.
화면은 로그인 화면으로 리다이렉트하지만 API는 그럴 수 없다. 호출자가 JSON을 파싱하는데
리다이렉트는 HTML 로그인 페이지로 도착해서, 브라우저에는 권한 문제가 아니라
파싱 오류로 나타난다. 그래서 API 거부는 JSON `403`이다.

**인가는 `cache_page` 바깥에 둔다.** 안쪽에 두면 인가된 호출자가 채운 캐시 본문이
그 뒤 누구에게나 제공된다. `tables`·`menus`가 해당하며 회귀로 고정했다.

**메서드 검사보다 인가가 먼저 실행된다.** 미인증 호출자가 어떤 메서드를 받는
경로인지 알아낼 필요가 없다. 인증된 호출자에게는 405 경계가 그대로 남는다.

세션 없음과 역할 불일치를 모두 403으로 답한다. 401과 403을 나누는 것은
D-042로 설계는 확정됐지만 D-035의 토큰 갱신 흐름과 함께 4A2에서 구현한다.
거부 본문에는 호출자의 역할도 허용 목록도 넣지 않는다. 거부된 클라이언트에게
쓸모가 없고 권한 모델을 그려주는 정보다.

## CSRF

쓰기 3개의 `@csrf_exempt`를 제거했다. 코드 주석도 `개발 편의. 운영 전 제거 권장.`이었다.

프런트엔드는 이미 준비돼 있었다. `order.html`의 주문 생성과
`kitchen_supervisor.html`의 취소·조리 진행이 모두 `X-CSRFToken` 헤더를 보낸다.
다만 그 토큰은 `csrftoken` 쿠키에서 읽으므로 쿠키가 반드시 있어야 한다.
로그인 페이지의 `{% csrf_token %}`이 쿠키를 설정하지만, 로그인과 첫 쓰기 사이에
쿠키가 지워지거나 회전하면 화면이 조용히 깨진다. 그래서 쓰기 기능이 있는 화면 4개에
`@ensure_csrf_cookie`를 붙였다. `b1_counter.html`은 읽기 전용이라 대상이 아니다.

`serve.html`과 `role_select.html`은 어느 뷰도 렌더하지 않는 미사용 템플릿이라 건드리지 않았다.

이것은 **인가**다. 인증 방식은 바꾸지 않았다. 여전히 역할 선택 + 공용 PIN 세션이며

### 세션과 CSRF 경계 (D-041)

세션이 이제 8개 API의 **유일한 인가 자격증명**이다. 그래서 잠재적이던 두 가지를 같이 닫았다.

- **세션 고정.** `login_view`가 역할을 넣기 전에 세션을 비우고(`flush`) CSRF 토큰도 회전한다.
  이전에는 로그인 전에 심어둔 세션 키가 로그인 후에도 유효했다. 공용 키오스크 브라우저에서
  현실적인 경로다. `cycle_key`가 아니라 `flush`인 이유는 전자가 **내용을 새 키로 옮기기** 때문이다.
  오늘 세션에는 `role`뿐이지만 익명 호출자가 심을 수 있는 값이 경계를 넘어오면 안 된다.
  로그아웃과도 같은 동작이 된다. `rotate_token`을 함께 부르는 이유는 세션 키가 자격증명의
  절반이기 때문이다. Django의 `login()`도 둘을 같이 한다. 실패한 로그인은 세션을 건드리지 않는다.
  권한 전이가 일어나지 않았고, 미인증 호출자가 세션 행을 만들어내게 두면 안 된다.
- **CSRF 거부도 JSON이다.** `CsrfViewMiddleware`는 모든 뷰 데코레이터보다 바깥이라
  토큰 없는 쓰기는 `require_api_roles`에 닿지 못하고 Django 기본값의 HTML로 거부됐다.
  API가 항상 JSON으로 답한다는 이 문서의 설계와 어긋난다. `CSRF_FAILURE_VIEW`를 두어
  API 경로는 JSON, 화면 경로는 기존 HTML 페이지로 답한다.
  **판정 기준은 모듈 이름이 아니라 가드 자신이다.** `require_api_roles`를 쓴 뷰는
  `answers_in_json` 표시를 달고, CSRF 실패 뷰는 그 표시를 본다. 모듈 이름 대조는
  `orders.views.api` 밖에 API가 생기면 조용히 틀려진다. 경로 접두사도 같은 이유로 쓰지 않는다.
  JSON 본문에 CSRF 실패 사유는 넣지 않는다. HTML 쪽은 Django 기본 동작대로 DEBUG에서만 보여준다.

**메서드별 주체는 가드가 직접 강제한다.** `by_method`는 메서드 이름을 검증하고,
HEAD는 GET의 주체를 상속한다. HEAD는 본문 없는 GET이므로 같은 기준을 넘어야 한다.
`require_http_methods`가 오늘 HEAD를 405로 막긴 하지만 그 데코레이터는 이 가드의 **안쪽**이라,
거기에 기대면 인가가 무관한 목록의 부수 효과가 된다. 메서드 이름 오타는 import 시점에 멈춘다.
오타 난 키는 영영 매칭되지 않아 그 메서드를 엔드포인트 기본값에 남기는데,
이 기능을 쓰는 유일한 엔드포인트에서 그 기본값은 "인증만"이다.

### 집계 우회는 엔드포인트를 지워서 닫았다

3차 리뷰가 같은 종류의 우회를 하나 더 찾았다. `stats-menu-counts`는 카운터 전용이고
메뉴별 `{name, qty, amount}`를 준다. 그런데 `kitchen-menu-summary`(인증만)가 메뉴별 미조리 수량을,
`menus`(인증만)가 단가를 주므로 둘을 `menu_item_id`로 합치면 메뉴별 미수령 매출이 나왔다.
`unit_price`는 주문 시점에 고정되므로 행사 중 가격이 그대로면 정확히 일치한다.

**`kitchen-menu-summary`는 호출하는 화면이 없었다.** 템플릿·static·앱 코드 어디에도 없고
`orders/urls.py`의 등록과 자기 정의, 그리고 테스트에만 나왔다. 사용자 결정으로
**경로와 뷰를 제거했다.** 주체를 새로 정하는 대신 표면을 없앤 것이라 D-040에 추측을 더하지 않는다.
`menus`는 주문 화면이 쓰므로 남는다. 단가만으로는 수량이 없어 재구성이 되지 않는다.

이 제거로 `orders/urls.py`의 API 경로는 9개에서 8개, 검사 단위는 10개에서 9개가 됐다.
`test_every_api_route_appears_in_the_matrix`가 그 수를 고정하므로 경로가 다시 생기면
매트릭스에 등재하지 않는 한 실패한다. 가드 없는 뷰로 되살려 보고 확인했다.

`test_baseline`의 조리 진행 회귀가 이 집계를 교차 확인에 쓰고 있었다. 그 단언만 걷어냈다.
같은 수량을 `order-detail`과 DB에서 각각 확인하는 단언이 남아 있어 불변조건 자체는 그대로다.

### 남는 인증 측 약점 — 4A2

인증 **방식**은 바꾸지 않았다. 아래는 단계3 당시 범위 밖으로 남긴 항목이다(D-041).

- **역할 회수가 세션에 닿지 않는다.** 유효성 검사가 `ROLE_TO_URLNAME`(화면 지도)을 보고
  실제 자격증명 저장소인 `settings.ROLE_PINS`를 보지 않는다. 환경에서 역할을 지워도
  이미 발급된 세션은 만료 전까지 계속 통과한다.
- **로그아웃이 CSRF 가능한 GET이다.** `<img src=".../logout/">` 한 줄로 세션이 날아간다.
- 4자리 PIN에 시도 제한이 없고 기본값이 저장소에 있다(BK-R002). 이 단계의 모든 통제가 그 아래에 있다.
- 404 응답은 여전히 HTML이고 `DEBUG` 기본값이 켜짐이다.

**2026-09-15 후속 상태:** 역할 회수·POST 로그아웃과 명시적 DEBUG 설정은 구현했고
주방 계정도 D-034에 따라 단일화했다. PIN 교체는 기존 세션을 끊지 않으며 시도 제한과 HTML 404는 남는다.
401/403 구분·토큰 수명·기기별 분리는 D-042로 설계 확정, JWT 구현은 후속이다.
메뉴·테이블 조회 주체와 자격증명 회수·교체 절차는 미정이고 주방 집계 경로는 제거했다.
Django 관리자(`/admin/`) 권한은 D-011이다.

브라우저 실제 여정은 검증하지 않았다. 서버 응답만 테스트했으므로
화면이 로그인 전에 호출하는 경로가 남아 있는지는 4B1의 브라우저 검사에서 확인한다.

BK-R001의 세 항목(익명 차단·CSRF 면제·매출 기밀성)을 저장소에서 닫고 회귀로 고정했으므로
증거 상태는 `Repo-fixed`가 되지만 **해결 상태는 운영 인수 전까지 Open이다.**
외부 노출·실제 자격증명·배포는 미실행이다.
schema·migration·번호/결제 계약·UI는 변경하지 않았다.
