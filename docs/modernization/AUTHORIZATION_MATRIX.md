# 단계 3 준비 — 권한 현황 측정과 D-003 결정표

2026-09-11 · [BK-R001](ANALYSIS_REPORT.md#bk-r001)(Critical, Open) · 단계 [3](BLUEPRINT.md#phase-3) 선행 준비.
측정 코드는 [권한 회귀](../../orders/tests/test_permissions.py)다.

**이 문서는 결정이 아니라 측정이다.** D-003은 여전히 대기 중이며 여기서 목표 매트릭스를 확정하지 않는다.
BLUEPRINT 단계 3이 "목표 매트릭스 확정 전에는 fixture/검사표만 준비한다"고 한 범위에 해당한다.
인가를 강제하는 코드 변경은 하지 않았다. `orders/views/api.py`는 기준 커밋과 바이트 동일하다.

## 측정 방법

Django 테스트 클라이언트로 실제 요청을 보내 응답을 분류했다. 행위자는 익명, 역할5개,
그리고 `GHOST`(세션은 있으나 서버가 발급한 적 없는 역할 문자열)의7가지다.
`GHOST`를 넣은 이유는 "세션이 있음"과 "서버가 아는 역할임"을 분리해서 봐야 하기 때문이다.

- `DENY`는 로그인 리다이렉트 또는401/403이다. 신원 때문에 멈춘 경우다.
- `OPEN`은 핸들러에 도달한 경우다. 업무 사유로 인한400도 `OPEN`으로 센다.
  요청이 신원 때문에 멈추지 않았다는 뜻이므로 인가 관점에서는 통과다.

각 요청은 보내는 주체를 빼면 모두 유효하다. 거부가 나온다면 원인은 인가뿐이도록 만들었다.

| 화면5개 | DENY | 자기 화면만 | 자기 화면만 | 주방3종 | 주방3종 | 주방3종 | DENY |
| **API9개 전부** | **OPEN** | **OPEN** | **OPEN** | **OPEN** | **OPEN** | **OPEN** | **OPEN** |

화면은 `@require_roles`로 막히고 API는 하나도 막히지 않는다.
`orders/views/api.py`는 세션이나 역할을 **한 번도 읽지 않는다**.
따라서 화면 단위 권한은 그 뒤의 API가 열려 있어 실효가 없다.

### 읽기 API — 7개 모두 익명200

| 엔드포인트 | 경로 | 현재 | 노출되는 것 |
| --- | --- | --- | --- |
| `tables` | `/orders/tables/` | OPEN | 테이블 목록 |
| `menus` | `/orders/menus/` | OPEN | 메뉴·가격 |
| `orders-collection` GET | `/orders/api/orders/` | OPEN | 주문 전체(필터·최대200건) |
| `order-detail` | `/orders/api/orders/<id>/detail` | OPEN | 단건 주문 상세 |
| `kitchen-menu-summary` | `/orders/api/kitchen/menu-summary` | OPEN | 주방 집계 |
| `stats-menu-counts` | `/orders/api/stats/menu-counts` | OPEN | 메뉴별 수량 |
| `stats-dashboard` | `/orders/api/stats/dashboard` | OPEN | **매출·결제수단·시간대 집계** |

마지막 세 행이 BK-R001의 매출 기밀성 항목이다.

### 쓰기 API — 3개 모두 익명 성공, CSRF 토큰 없이도 성공

| 엔드포인트 | 메서드 | 현재 | 영향 |
| --- | --- | --- | --- |
| `orders-collection` | POST | OPEN·201 | 주문 생성 |
| `order-status` | PATCH | OPEN·200 | 주문 상태 변경(취소 포함) |
| `order-item-progress` | PATCH | OPEN·200 | 조리 진행 수량 변경 |

세 엔드포인트 모두 `@csrf_exempt`다. 주석에 `개발 편의. 운영 전 제거 권장.`이라고 적혀 있다.
CSRF를 강제하는 클라이언트로도 토큰 없이 통과한다. 같은 클라이언트의 로그인 POST는403이므로
이것은 검사가 꺼진 것이 아니라 면제가 적용된 결과다.

### 그 외 측정한 경계

- **역할 교차:** ORDER 역할이 조리 진행 변경과 주문 취소를 모두200으로 수행한다.
  BK-R001이 지목한 사례이며 D-003에서 가장 달라질 가능성이 큰 지점이다.
- **로그아웃:** 세션을 비워도 API 접근이 그대로다. 이 앱의 유일한 회수 수단이 API에 닿지 않으므로
  "만료된 세션"과 "세션 없음"은 매트릭스에서 같은 행이다.
- **메서드:** `require_http_methods`의405만 실제로 동작하는 유일한 관문이다.
  후속 단계가405를 인가로 오해하지 않도록 고정했다.

## D-002/D-031/D-032와의 관계

BK-R001의 "미확인" 항목은 원래 **외부 노출 범위**와 **승인된 역할 매트릭스** 두 가지였다.
D-031이 외부 인터넷 접속 허용을 확정하면서 전자가 답해졌고, 이는 완화가 아니라 **노출 상향**이다.
익명 쓰기가 가능한 API가 공개 경로에 놓이는 구성이 된다.
D-032가 역할별 공용 계정을 확정했으므로 매트릭스의 주체 축은 이제 정의할 수 있다.
남은 미확인은 D-003의 경로·메서드별 허용뿐이다.

## D-003에서 답해야 할 것

아래는 질문이며 제안된 답이 아니다. 각 행은 위 측정의 현재 값을 함께 적었다.

1. 조회 API를 역할별로 나눌 것인가. 특히 `stats-dashboard`·`stats-menu-counts`를
   B1_COUNTER 전용으로 둘지, 통계 조회 계정을 따로 둘지(D-032의 남은 결정과 연결).
2. 주문 취소(`order-status` → CANCELLED)를 누가 할 수 있는가. 현재는 전원이다.
3. 조리 진행 변경을 주방3역할로 한정할 것인가. 현재는 전원이다.
4. 홀/포장 총괄이 자기 범위 밖 주문을 변경할 수 있는가.
   **기존 전체 주방 화면 접근을 조용히 제한하지 않는다**는 제약이 BLUEPRINT에 있다.
5. 익명 접근을 완전히 차단할 것인가. 차단 시 현재 화면이 로그인 없이 호출하는 경로가 있는지
   확인해야 한다(이 문서는 서버 측만 측정했고 브라우저 여정은 단계 3 구현에서 확인한다).
6. CSRF 면제를 언제 제거하고 정상 클라이언트에 토큰을 어떻게 전달할 것인가.
7. 거부 응답 형식. 화면은 리다이렉트, API는 JSON401/403 중 무엇으로 통일할 것인가.

## 남는 경계

이 측정은 서버 응답만 본다. 브라우저 여정·Supabase 구독·관리자(`/admin/`)는 범위 밖이다.
Django 관리자 권한은 D-011에서 따로 다룬다.
통과하는 회귀가 인가가 존재한다는 뜻이 **아니다.** 대부분의 단언은 인가가 없음을 기록한 것이다.
단계 3 구현 시 `OPEN`으로 적힌 기대값은 승인된 매트릭스로 교체해야 하며, 교체 전에 먼저 실패해야 한다.
BK-R001은 Open이며 이 준비 작업으로 종료되지 않는다.
