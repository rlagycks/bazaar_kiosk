# 브라우저의 외부 Realtime 제거 (4B2)

상태: 로컬 구현과 검증. 결정은 [D-056](DECISIONS.md). 위험: BK-R018, BK-R029, BK-R020.
**스키마 변경과 마이그레이션이 없다. 외부 서비스 설정은 건드리지 않았다.**

## 무엇이 있었나

주방 화면은 세 가지를 하고 있었다.

1. CDN에서 외부 Realtime SDK를 내려받았다. 저장소가 고정하지 않는 코드가 운영자 화면에서
   실행됐다(BK-R029).
2. 프로젝트 URL과 익명 키를 **자기 HTML에 담아** 모든 주방 화면에 전달했다.
3. 그 키로 `orders_order`와 `orders_orderitem` 테이블 변경을 직접 구독했다.

세 번째가 핵심이다. Django의 신뢰 경계 옆에 두 번째 경계가 생긴다. 구독이 화면에 보이는 것보다
더 많이 읽을 수 있는지는 이 저장소가 검증할 수 없는 외부 Row Level Security에 달려 있었고,
익명 키는 RLS의 대체물이 아니다(BK-R018). 구독이 2초 안에 붙지 않으면 폴링으로 넘어가는
경합도 있었다.

## 무엇을 했나

| 이전 | 지금 |
| --- | --- |
| CDN `<script>`로 외부 SDK 로드 | 없음. 페이지가 여는 코드는 이 서버의 정적 파일뿐 |
| URL·익명 키를 HTML에 주입 | 없음. `_supabase_context`, 두 설정, `.env.example` 항목 제거 |
| 테이블 변경 직접 구독 | 없음. 화면은 자체 인증 API만 호출한다 |
| 구독 실패 시 5초 폴링 | 없음. 사용자 지시로 폴링도 함께 걷어냈다 |

## 자동 갱신이 없다는 사실

사용자 지시(2026-09-20): **"어차피 SSE로 갈 거고 지금 서비스 중이 아니니 폴링도 같이 없애자."**

그래서 10D의 자체 SSE가 들어올 때까지 주방 보드는 **스스로 갱신되지 않는다.** 바뀌는 경우는
세 가지다. 새로고침 버튼을 누를 때, 카드에서 취소·수량을 조작할 때, 그리고 탭으로 돌아올 때
한 번 읽는다. 탭 복귀는 타이머가 아니라 단발 요청이다. 탭을 열어 둔다고 폴링하지 않는다.

**탭을 바꾸지 않는 배치에서는 그 한 번조차 일어나지 않는다.** 전용 디스플레이에 전체화면으로 띄워 두면
`visibilitychange`가 발생하지 않으므로, 그 화면은 페이지를 연 뒤 카드 조작 외에 **영구히 갱신되지 않는다.**
데스크톱에서 창이 다른 앱에 가려지기만 한 경우도 마찬가지다. 주방 보드는 바로 그런 설치 형태가 흔하다.

상태 줄은 이 사실을 **말한다.** "목록 읽은 시각 hh:mm:ss · 대기 주문 N건 · 자동 갱신 안 함,
새로고침을 눌러 주세요". 멈춘 보드가 조용한 주방처럼 보이면 8B에서 막 고친 것과 같은 종류의
실패다. 시각을 앞세운 것도 같은 이유다.

그 시각은 **목록을 읽은 시각**이지 화면을 그린 시각이 아니다. 단건 갱신은 목록을 읽지 않으므로
이 시각을 밀지 않는다. 읽기에 실패하면 카드를 지우지 않고 상태 줄만 "읽기 실패 · 화면은 hh:mm:ss
목록입니다"로 바꾼다. 새로고침은 누르는 동안 "읽는 중…"으로 바뀐다. 이제 이것이 유일한 갱신
수단이기 때문이다.

**개수 두 개의 단위가 다르다.** "대기 주문 N건"은 화면의 `MODE_SCOPE` 필터를 거친 뒤이고,
"서버에 M건 대기"는 서버가 권한으로 좁힌 전체다. 홀 보드에서 두 숫자가 크게 어긋나 보일 수 있다.
8B에서 넘어온 것이고 이 단계가 이 문장을 유일한 고지로 격상시켰으므로 여기에 적어 둔다.

## 표시만이 아니라 쓰기도 낡는다 (받아들인 위험)

`prepared_qty`는 **절대값 last-writer-wins**다. 서버에 버전이나 기대값 검사가 없고, 화면이 보내는
값은 마지막 렌더의 DOM 속성에서 계산된다. 두 보드가 같은 항목을 보고 있을 때 한쪽이 먼저 올리면
다른 쪽은 자기 화면의 낡은 숫자로 계산해 보낸다. 같은 값이면 서버는 아무 일도 하지 않고, 두 명이
두 개를 조리했는데 기록은 하나로 남는다. 버튼은 성공하고 숫자만 틀리므로 화면에 오류가 보이지 않는다.

5초 폴링이 있을 때 이 창은 최대 5초였다. **지금은 누군가 새로고침을 누를 때까지 무한이다.**
BK-R013의 "stale absolute progress" 항목에 이 파급을 적어 두었다.

10D 이전에 운영한다면 **한 항목을 두 보드에서 동시에 조작하지 않는다**를 운영 지침에 넣어야 한다.
근본 해결은 10C의 revision 일관성과 10D2의 적용 버전 검사다.

## 외부 정리는 아직 남아 있다

**이 단계는 외부 서비스 쪽 설정을 하나도 바꾸지 않았다.** 이 앱이 그 값을 읽는 경로는 제거했지만,
브라우저가 더는 연결하지 않을 뿐 외부에 남아 있는 권한은 그대로이고, 배포 환경에 남은 변수도 따로
지워야 한다. 아래는 **실행 목록이 아니라 인계 목록**이며, 각 항목은
별도 승인과 운영 담당자의 실행이 필요하다.

| 항목 | 왜 |
| --- | --- |
| Realtime publication에서 `orders_order`·`orders_orderitem` 제거 | 구독자가 없어도 발행은 계속된다 |
| 익명 역할의 테이블 권한·RLS 정책 재확인 | 키가 유출된 적이 있다면 구독 제거만으로 닫히지 않는다 |
| 노출됐던 익명 키 회수·재발급 | 이 저장소 이력과 배포된 페이지 소스에 실렸을 수 있다 |
| 외부 프로젝트 자체의 존치 여부 판단 | DB 이전(12A3)과 함께 결정할 사안이다 |
| 배포 환경·시크릿 저장소의 `SUPABASE_URL`·`SUPABASE_ANON_KEY` 삭제 | 앱은 더는 읽지 않지만 값은 그대로 남아 유출 표면이 유지된다. `<NAME>_FILE` 방식이면 마운트된 파일도 대상 |
| **회수 전에** 외부 접근 로그 확보 | 키를 먼저 돌리면 그 키가 예상 밖 origin에서 쓰였는지 확인할 기회가 사라진다 |

이 목록은 문서 안에서만 살아 있으면 닫을 사람이 없다. 4A3에서 프록시 IP 위험을 이슈로 등록해
닫은 선례를 따라 **담당자·기한과 함께 이슈로 등록해야 한다.**

**BK-R018은 닫히지 않는다.** 위 목록이 실행되고 자체 SSE 인가까지 검증돼야 닫힌다.
BK-R029는 브라우저가 외부 코드를 더는 불러오지 않으므로 이 단계에서 닫는다.
BK-R020은 성격이 바뀐다. "연결 상실 후 폴링 복귀"가 아니라 "SSE 이전에는 자동 갱신 없음"이고,
10D에서 닫는다.

### 실행 중인 서버에 대한 HTTP 기록 (2026-09-20)

격리된 임시 PostgreSQL(포트 55471, 전용 compose 프로젝트)에 마이그레이션하고 개발 서버를
127.0.0.1:8010에 띄워 실제 요청을 보냈다. 검사 후 서버를 종료하고 `down -v`로 제거했다.
기존의 무관한 컨테이너는 건드리지 않았다.

| 검사 | 결과 |
| --- | --- |
| 로그인 후 `/orders/kitchen/`, `/order/`, `/b1-counter/` | 200, 각각 외부 origin `src`/`href` **0개** |
| 세 페이지의 supabase·cdn·realtime·createClient 토큰 | **0** |
| 세 페이지의 `setInterval` | **0** |
| 주문 생성 → 주방 보드 조회 | 201 → `mode=queue count=1 total=1 has_more=false` |
| 계정 비활성화 후 같은 토큰으로 보드 조회 | **401** |
| 비활성화 후 주방 페이지 | **302 → 로그인** |
| 비활성화 후 refresh | **401** |

**한계:** 이것은 HTTP 클라이언트 기록이지 실제 브라우저 네트워크 기록이 아니다. 이 환경에서
Chrome 확장과 Playwright 브리지가 모두 연결되지 않아 카드가 요구하는 V-BROWSER를 실행하지
못했다. 브라우저가 실제로 여는 하위 요청 목록, 끊김 상태의 화면 동작, 실기기 여정은 아직
검증되지 않았다. 배포 전에 실제 브라우저에서 한 번 확인해야 한다.

## PR #74 리뷰 결과 (2026-09-20)

코드·보안·아키텍처 리뷰 에이전트 3개. 코드 리뷰는 APPROVE, CRITICAL/HIGH 없음. 보안 리뷰가 HIGH 2건을 올렸고
**둘 다 코드 문제가 아니라 이 단계가 남기는 잔여 위험**이다. 아래에 그대로 적는다.

### HIGH-1 — 권한이 회수돼도 열려 있는 화면은 그대로 남는다 (받아들인 위험)

폴링이 없으므로 요청이 나가지 않고, 요청이 없으면 401도 없고, 401이 없으면 화면은 권한을 잃은 사실을 모른다.
키오스크처럼 **계속 앞에 떠 있는 탭**은 `visibilitychange`도 일어나지 않는다. 그래서 근무 중 계정이 비활성화되면
그 화면은 마지막으로 읽은 주문 목록(테이블 번호, 항목, 요청사항)을 누군가 새로고침을 누르거나 카드를 조작할 때까지
계속 보여 준다. 5초 폴링은 5초 안에 이 상태를 끝냈다.

위의 HTTP 기록은 **요청이 나가는 경우**만 확인했다(401·302·401). 아무도 건드리지 않는 화면은 확인하지 않았고,
그게 새로 생긴 노출 구간이다.

이것은 D-056의 직접적인 결과다. 사용자가 서비스 중이 아니라는 전제로 폴링 제거를 지시했다. **실제 행사 운영
전에는 10D의 SSE가 반드시 선행되어야 하며**, 그 전에 운영한다면 이 위험을 운영 지침에 명시하거나, 데이터
폴링이 아닌 저빈도 인증 확인을 따로 승인받아야 한다. 이 단계에서는 타이머를 다시 넣지 않는다. 사용자의 지시가
"폴링을 없앤다"였고, 타이머 없음은 테스트로 고정돼 있다.

### HIGH-2 — 코드 제거는 키를 회수하지 않는다

리뷰가 `git log --all -p`로 저장소 전 이력을 확인한 결과 **실제 URL이나 키 값이 커밋된 적은 없다.** 항상 빈
문자열이거나 환경 변수 참조였다. 그러나 이 기능이 살아 있던 동안 익명 키는 **모든 주방 화면 HTML에 실려
나갔다.** 페이지 소스를 본 사람, 응답을 가로채거나 캐시한 곳에는 그 값이 있다. 코드를 지운다고 그 키가 무효가
되지 않고, 외부 publication과 RLS도 그대로다. 위의 인계 목록이 실행되어야 닫힌다. **BK-R018은 열려 있다.**

### 아키텍처 리뷰 — 조건부 승인, HIGH 3건

**HIGH — 고지가 스스로 거짓말을 했다(고침).** 상태 줄의 시각이 목록을 읽은 시각이 아니라 화면을 **그린** 시각이었다.
단건 갱신은 목록을 읽지 않고도 다시 그리므로, 09:00에 연 보드에서 11:30에 카드 하나를 조작하면 상태 줄이
"읽은 시각 11:30"으로 바뀐다. 목록은 09:00 것이고 그 사이 들어온 주문은 화면에 없다. 뒤에 붙은 "자동 갱신 안 함"이
오히려 앞의 시각을 더 믿게 만든다. 이 단계가 유일한 완화책으로 내세운 고지가 스스로를 무효화하고 있었다.
목록을 읽은 시각만 기록해 쓰도록 고쳤고 회귀 테스트로 고정했다.

**HIGH — stale 쓰기 발산(받아들임, 문서화).** 위의 "표시만이 아니라 쓰기도 낡는다" 절.

**HIGH — BK-R029 과다 종결(고침).** 위험 이름이 "가변 CDN 스크립트와 **콘텐츠 보안 정책 검증 부재**"인데 앞쪽만
처리하고 "해소"로 닫았다. 저장소에 CSP 헤더가 없고, 다른 문서 세 곳이 아직 CSP를 4B2가 할 일로 가리키고 있었다.
"부분 해결(CSP 미결, 12A1 대기)"로 고치고 세 포인터를 12A1로 정정했다.

**MEDIUM들(반영).** 읽기 실패가 카드를 전부 지워 버렸다. 폴링이 있을 때는 5초 뒤 스스로 복구됐지만 지금은 사람이
누를 때까지 빈 화면이다. 이전 렌더를 유지하고 상태 줄만 바꾸도록 고쳤다. 새로고침 버튼에 진행 표시를 넣었다.
이제 유일한 갱신 수단이다. 타이머 울타리가 재귀 `setTimeout`과 공유 JS 파일을 보지 못했으므로 넓혔다.
10B·10C·10D1·10D2와 4B2 자신의 롤백이 "보호된 자체 폴링"이라는 **존재하지 않는 대상**을 가리키고 있어, 다섯 줄 모두에
10D2가 신규 작성한다는 주석을 달았다. 탭을 바꾸지 않는 배치와 개수 단위 불일치도 위에 적었다. 인계 목록에 배포
환경 변수 삭제와 회수 전 로그 확보를 더했다.

### MEDIUM — 벤더 이름만 막으면 문 하나만 닫힌다

기존 테스트는 `supabase` 같은 키워드 목록이라, 나중에 인라인으로 `fetch("https://…")`나 `new WebSocket("wss://…")`를
넣으면 걸리지 않았다. 성질 자체를 고정하도록 바꿨다. 라이브 템플릿에 **절대 URL이 하나도 없어야 하고**,
`EventSource`·`WebSocket`·`Worker`·`importScripts`를 열지 않아야 한다. 10D가 SSE를 넣을 때는 이 테스트를 고치면서
무엇이 바뀌는지 밝히게 된다. CSP `connect-src`는 여전히 열린 항목이다(BK-R011).

코드 리뷰 MEDIUM/LOW는 `queueOrderRefresh`의 디바운스가 구독 제거 후에도 남은 이유가 어디에도 없다는 것이었다.
한 주문의 여러 항목을 빠르게 누르면 여전히 버스트가 생기므로 유지하고, 주석으로 이유를 적었다.

## 남은 것

- 위의 외부 정리 인계 목록. 승인과 운영 담당자의 실행이 필요하다.
- 실제 브라우저 네트워크 기록(V-BROWSER).
- 자체 SSE 서버·클라이언트와 재접속·응답 순서는 10D1·10D2.
- 그때까지 주방 보드는 수동 갱신이다. 실제 행사 운영 전에 SSE가 반드시 들어와야 한다.
