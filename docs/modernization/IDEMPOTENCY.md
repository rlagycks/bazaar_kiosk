# 6A — 중복 요청 경계 (D-049)

상태: 구현과 로컬 브라우저 검증. BK-R012의 저장소 쪽 수정이며 운영 인수는 별도다.
화면 구성은 그대로다. 사람 눈에 보이는 변화는 없다.

## 무엇이 문제였나

자원봉사자가 휴대폰으로 저장을 누른다. 응답이 오지 않는다. 다시 누른다.
**주방에 같은 주문이 두 장 뜨고 손님은 두 번 계산된다.**

서버는 재전송과 "같은 메뉴를 시키는 다음 손님"을 구분할 수단이 없었다. 분석 당시
PG에서 8스레드로 같은 요청을 16번 보내면 주문 16개가 생겼다(BK-R012).

## 확정된 계약 (D-049, 에이전트 판단)

| 항목 | 동작 |
| --- | --- |
| 식별 | 화면이 만든 `request_id`. 저장 1회당 1개 |
| 재전송 | 이미 만든 주문을 그대로 돌려준다. **200**(생성은 201) |
| 같은 ID·다른 내용 | **409**. 덮어쓰지도, 조용히 옛 주문을 주지도 않는다 |
| 같은 ID·다른 계정 | **409**. 남의 화면 주문을 넘겨주지 않는다 |
| ID 없음·형식 오류 | **400** |
| 만료 | **없음** |

## 어떻게 고쳤나

- `OrderRequest`(키·역할·지문·주문)를 추가했다. 행은 **주문과 같은 트랜잭션에서** 쓴다.
  그래서 주문이 있으면 행이 있고, 주문이 롤백되면 행도 없다. 거부된 시도는 ID를 다시 쓸 수 있다.
- 동시에 같은 ID가 둘 오면 유니크 인덱스가 진 쪽을 막는다. 진 쪽은 이긴 쪽이 커밋할 때까지
  기다렸다가 `IntegrityError`를 받고 **자기 트랜잭션 전체를 롤백**한 뒤 이긴 쪽 주문을 돌려준다.
  주문·품목·할당한 번호가 함께 사라지므로 번호도 낭비되지 않는다(D-047의 성질).
- 지문은 주문을 정하는 필드만 본다(메뉴·수량·모드·테이블·결제·금액·요청사항).
  값은 문자열로 맞춰 비교한다. `8000`과 `"8000"`, `dine_in`과 `DINE_IN`은 같은 주문이다.
  다만 `None`과 `0`은 구분한다 — "받지 않았다"와 "0원 받았다"는 다른 주장이다.
  (2026-09-18 코드 리뷰가 금액·모드 정규화 누락을 지적해 고쳤다. 현재 화면은 항상 같은
  형식으로 보내므로 잠재 결함이었지만, 다른 클라이언트나 수동 재시도에서 정상 재전송이
  409로 거부될 수 있었다.)
- 화면은 저장을 누를 때 ID를 만들고, **저장에 성공하면 버린다.** 실패하면 남겨서 다시 누르면
  재전송이 된다. 그리고 **주문 내용을 건드리면 버린다** — 장바구니·테이블·결제·금액 어느 것이든.
  이게 없으면 실패 뒤 수정한 주문이 409로 거부되고 수정이 안 된 것처럼 보인다.

## `crypto.randomUUID`를 그냥 쓰지 않은 이유

`crypto.randomUUID`는 **보안 컨텍스트에서만** 존재한다. 평문 HTTP로 열면 없다.
그래서 `getRandomValues`(보안 컨텍스트 제한이 없다) 대체 경로를 넣었고, 그것마저 없으면
시간+난수로 만든다. 서버의 형식 규칙을 모든 경로가 만족하는지 테스트로 고정했다.

**다만 이 대비는 현재로선 방어적이다.** 실제로 평문 HTTP에서 확인해 보니 그 전에 로그인이
안 된다(아래).

## 검증

| 검사 | 결과 |
| --- | --- |
| 전체 PostgreSQL 테스트 | 212개(마이그레이션20+앱192), skip0 통과 |
| `orders/tests/test_idempotency.py` | 24개 통과(재전송, 번호 미소모, 서로 다른 시도, 내용·계정 충돌, 형식 검증, 실패 시 ID 해제, 만료 없음, 동시 제출, 화면 연결, 지문 정규화) |
| `scripts/test_request_id.cjs` | 7개 통과(보안 컨텍스트·비보안·예외·crypto 없음·중복 없음·서버 형식). Node 전체 30개 |
| 실제 Chromium 더블탭 | 8개 통과 |

브라우저 검사는 응답을 0.7초 지연시켜 **첫 응답이 오기 전에 두 번째 탭**이 들어가게 했다.
두 요청이 같은 ID를 싣고, 201·200 하나씩 받고, **같은 주문 하나**를 가리켰다.
이어서 다음 주문은 새 ID로 201을 받았고 주방 화면에는 주문이 **3개가 아니라 2개** 떴다.

**검사가 보지 못한 것:** 브라우저 검사는 `127.0.0.1`에서 돌았고 브라우저는 localhost를
보안 컨텍스트로 친다(`isSecureContext=true`). 즉 **비보안 컨텍스트 대체 경로는 브라우저에서
실행되지 않았다.** 그 경로는 Node 테스트로만 확인했다. 통과 목록만 보면 확인한 것처럼 보이므로 적어 둔다.

## 이 과정에서 확인한 별개 문제 — 평문 HTTP에서는 로그인이 안 된다

대체 경로를 진짜 비보안 컨텍스트에서 보려고 LAN 주소(`http://192.168.x.x:8099`)로 열었더니
**메뉴가 뜨지 않았다.** 원인은 6A와 무관하다.

- `JWT_COOKIE_SECURE = True`라서 refresh 쿠키 `bk_refresh`가 `Secure`로 나간다.
- 평문 HTTP에서는 브라우저가 그 쿠키를 **저장하지 않는다.**
- 그래서 로그인 POST가 302로 성공한 뒤 `/orders/order/`가 다시 로그인으로 돌아온다.
  브라우저에 남는 쿠키는 `csrftoken`뿐이다.

**배포 후보(4A3)는 프록시가 평문 HTTP 80을 공개한다.** TLS는 12A1로 미뤘다.
두 사실을 합치면 **그 구성에서는 브라우저로 로그인할 수 없다.** 4A3 검증은 curl로 한
로그인 제한 확인이었고 curl은 `Secure` 속성을 강제하지 않아서 드러나지 않았다.

이것은 결함이라기보다 **12A1이 TLS를 반드시 포함해야 한다는 제약**이다. 이번 PR에서 코드로
바꾸지 않았고 [배포 후보 문서](DEPLOYMENT_CANDIDATE.md)에 같은 내용을 적었다.

## 남은 것

- 배포 후 새로고침하지 않은 탭은 주문이 400으로 거부된다(D-049의 의도된 결과).
  현장에서는 화면을 열 때 새로 불러오므로 실무 영향은 작다고 보지만, 인수 때 확인할 항목이다.
- **쓰기 경로에 속도 제한이 없다(2026-09-18 보안 리뷰 지적).** 인증된 기기는 새 ID를 계속
  만들어 주문을 무한히 생성할 수 있고, 그만큼 `OrderRequest` 행도 늘어난다. 이번에 생긴 문제가
  아니라 기존 공백이며(로그인에는 D-045 제한이 있다) 6A가 그 경계를 더 눈에 띄게 만들었다.
  주문 품목 배열의 길이 상한이 없는 것도 같은 성격의 기존 공백이다.
- `OrderRequest.order`는 `PROTECT`다. 주문을 지우면 늦은 재전송을 막던 기록이 함께 사라지므로,
  삭제가 허용되는지(**D-011**)가 정해지기 전까지는 조용히 따라 지우지 않고 실패하게 뒀다.
- 상태 변경·조리 진행 같은 다른 명령에는 아직 이 경계가 없다. 6B 범위다.
- 카운터 화면은 주문을 만들지 않으므로 이번 변경 대상이 아니다.
- 미사용 `serve.html`은 요청 ID 없이 주문을 POST하는 코드를 그대로 갖고 있다. 어떤 뷰도
  렌더링하지 않고, 4B1에서 넣은 **참조되면 실패하는 테스트**가 다시 연결되는 것을 막는다.
  삭제는 11단계 정리 범위다(2026-09-18 코드 리뷰 지적).
- BK-R012는 저장소에서 닫혔고 운영 인수 전까지 Open이다.
