# 10D2 — 주방 SSE 클라이언트·재접속·응답 순서 (D-019, D-061)

브랜치 `phase-10d2-kitchen-client`, 기준 `develop` affc842. 상태: 구현 완료.

## 문제

10D1이 서버가 화면에 먼저 말하게 했다. 이제 화면이 들어야 하는데, 4B2 이후 주방 보드는
새로고침 버튼과 탭 복귀에만 읽는 수동 화면이었다. 붙이는 것 자체보다 어려운 것은 카드가
적은 대로 **"연결 성공만으로 복구 완료가 아니다"**라는 점이다. 연결이 CONNECTING에 걸려 있거나,
허브가 죽은 채 heartbeat만 오거나, 늦은 응답이 최신 화면을 덮거나, 로그아웃된 탭이 계속 읽는
경로가 전부 열려 있다. 그것이 BK-R020과 BK-R033이다.

## 사용자가 고른 것 (D-019의 마지막 관문)

> **"5초 후퇴 폴링"**, **"보이는 탭만 연결"**

## 설계 — 스케줄러 하나

`orders/static/orders/ui/kitchen_live.js`. 보드의 **읽는 시점**을 정하는 곳은 이 파일 하나이고,
페이지의 다른 어떤 코드도 읽지 않는다. 주문 데이터는 10C snapshot에서만 온다(스트림에는
payload가 없다, D-058).

```
poll while NOT (stream open AND hub_ok AND complete snapshot applied AND last read succeeded)
```

D-019 그대로다. heartbeat는 증거가 아니다 — `ready`와 heartbeat에 실린 `hub_ok`가 거짓이면 죽은
연결과 똑같이 폴링한다. `change`에는 `hub_ok`가 없지만 도착 자체가 증거다: 허브는 DB 읽기에 성공한
뒤에만 보낸다(PR #80 리뷰, 아래).

| 상황 | 동작 | 상태 줄 |
| --- | --- | --- |
| 페이지 열림 | 스트림 열고 snapshot 한 번 읽음. `ready`가 오면 한 번 더(연결 중 바뀐 것) | 연결 중 · 5초마다 다시 읽음 |
| `ready` + `hub_ok` + 완전한 snapshot | 폴링 멈춤 | **실시간 연결** |
| `change` | `hub_ok`를 참으로(허브가 읽었다는 뜻). `since=` 커서로 읽기. 읽는 중 온 것은 하나로 합침 | 실시간 연결 |
| `heartbeat` `hub_ok:false` | 폴링 시작 | 서버 감지 지연 · 5초마다 다시 읽음 |
| snapshot `complete:false` (500건 상한) | 스트림이 건강해도 폴링 | 5초마다 다시 읽음 · 서버에 N건 대기 |
| 읽기 실패 | 카드 유지, 폴링 | 읽기 실패 · 화면은 hh:mm:ss 목록입니다 |
| `EventSource` CONNECTING | 브라우저 재시도에 맡김. 폴링 | 연결 중 · 5초마다 다시 읽음 |
| `EventSource` CLOSED (비 200·503·거절) | 2초→4초→…→30초 상한으로 직접 다시 엶. 폴링 | 연결 중 |
| `closed: unverified` | 같은 백오프로 재접속. 폴링 | 연결 중 |
| `closed: revoked` / `reauthenticate` | **전부 끝냄** — 스트림·타이머·읽기. 로그인으로 | 로그인 화면으로 이동합니다 |
| 읽기 중 `AuthenticationLost` | 위와 같음 (auth.js가 이미 로그인으로 보냄) | — |
| heartbeat 두 주기 침묵 | 죽은 연결로 보고 닫고 다시 엶 | 연결 중 |
| 탭 숨김 / `pagehide` | 스트림 닫고 폴링 멈춤. 진행 중 읽기는 늦은 것으로 | — |
| 탭 보임 / `pageshow` | 새 스트림 + 읽기 한 번. `ready`가 오면 한 번 더(페이지 열림과 같음) | 연결 중 → 실시간 연결 |
| `EventSource` 없는 브라우저 | 폴링만. 실시간이라 말하지 않음 | 연결 중 · 5초마다 다시 읽음 |

### 응답 역전은 읽기 하나와 epoch으로 막는다

카드는 "같은 세대 43→42 역전 방어"를 `appliedRevision`으로 요구했다. 같은 generation·scope
안에서 D-059의 버전은 순서가 있다(D-058의 잠긴 행이 "나중 번호"와 "나중 커밋"을 같은 말로
만든다). 그래도 비교하지 않는 이유는 **필요가 없어서**다 — 처음 적었던 "버전은 순서가 없다"는
generation을 넘는 경우에만 참이었고, PR #80 아키텍처 리뷰가 바로잡았다.

- **읽기는 한 번에 하나.** 읽는 중 온 요청은 "끝나면 한 번 더"로 합쳐진다. 같은 epoch 안에서는
  역전이 생길 **수 없다** — 두 번째 읽기는 첫 번째가 적용된 뒤에야 나간다. 역전 대부분을 막는
  것은 이것이지 epoch이 아니다.
- **일시정지가 epoch을 올린다.** epoch이 하중을 받는 곳은 일시정지 경계뿐이다: 탭을 숨긴 채
  응답이 오면(새 읽기가 없어 순번이 못 막는다) epoch이 달라 버려지고, 다시 보여 새 읽기가 먼저
  적용된 뒤 옛 응답이 와도 마찬가지다. 테스트가 두 순서를 모두 재현한다.
- **쓰기 전에 나간 읽기는 거부가 아니라 수렴이다.** 취소 PATCH가 끝났을 때 그 전에 나간 읽기가
  아직 돌아오지 않았으면 그 응답은 적용되고, PATCH가 요청한 읽기가 그 뒤에 나가 카드를 지운다.
  쓰기 응답을 그리지 않으므로 늦은 목록이 되살릴 것은 보드에 이미 있던 것뿐이라 화면은 바뀌지
  않는다. 카드의 "삭제/취소 뒤 늦은 목록 거부"는 이 뜻이며 노드 테스트가 순서를 고정한다.

### 쓰기 응답은 그리지 않는다

BK-R033의 경합은 목록 읽기와 단건 읽기라는 **두 경로**가 있어서 생겼다. 이제 PATCH 뒤에는
응답을 그리지 않고 같은 스케줄러에 읽기를 요청한다. 거절(409)을 받아도 마찬가지다 — 다른
사람이 이미 바꿨을 수 있다. 경로가 하나라 늦은 목록이 덮을 최신 단건이 없다. 왕복 하나가
늘지만 `since=`가 있어 대개 `unchanged`(4왕복·1ms)다.

### 보이는 탭만 연결한다

TLS 전(12A1)이라 HTTP/1.1이고 브라우저는 출처당 연결을 약 6개로 제한한다. 주방 탭 6개면
snapshot 요청 자체가 막힌다. 서버도 워커당 24개가 상한이다(10D1). 숨겨진 탭은 낡은 보드를
가장 안 보는 곳이기도 하다. `pagehide`에 닫는 것은 BFCache 때문이다 — 열린 연결을 쥔
페이지는 캐시되지 않고, 캐시에서 돌아온 페이지는 그동안을 전부 놓쳤다.

## 리뷰 반영

- 코드 리뷰 HIGH 1: **epoch 검사에 자기만의 테스트가 없었다.** 제가 "epoch 검사를 빼면 실패한다"고
  적은 변이는 seq 검사까지 같이 뺀 것이었다. epoch만 빼면 18건이 전부 통과했다 — "숨김 → 보임 →
  새 응답 먼저 → 옛 응답" 시나리오는 요청 순번(seq)만으로도 막히기 때문이다. epoch이 진짜로
  하중을 받는 것은 **숨긴 채로 옛 응답이 도착하는** 경우(새 읽기가 아직 없어 seq가 도울 수 없다)고,
  거기엔 테스트가 없었다. 추가했고, 이제 epoch만 빼면 그 테스트가 실패한다.
- 코드 리뷰 MEDIUM: 읽기가 계속 실패하는 동안 `change`마다 같은 오류를 두 번씩 로그했다(읽기 시작·
  실패 보고 각각). 오류가 바뀔 때만 로그하고 복구도 한 줄 남기도록 바꿨다.
- 코드 리뷰 LOW: 탭을 다시 보일 때 백오프 지연을 초기화하지 않았다. 새 탭은 옛 스트림의 실패로
  벌받지 않도록 2초부터 다시 시작한다(테스트 추가).
- 보안: CRITICAL/HIGH/MEDIUM 없음. LOW 하나 — 브라우저 스크립트가 대상 DB가 일회용인지
  확인하지 않았다. 모든 쓰기 전에 DB 이름이 `bk_dev*`/`bk_test*`가 아니면 거부하도록 넣었다.
  확인하고 문제없다고 한 것: 같은 출처 검사(스케줄러·auth.js 양쪽), `since=` 커서가 서버 응답에서만
  오는 점, 상태 줄이 `textContent`만 쓰는 점, 읽기 하나·백오프 상한으로 증폭 경로가 없는 점,
  회수 뒤 stale 탭이 `resume`으로 되살아나지 않는 점.

### PR #80 리뷰 (병합 전, 코드·보안·아키텍처 — CRITICAL/HIGH 없음)

- **아키텍처 MEDIUM, 제가 쓴 근거의 반증:** "D-059의 버전은 순서가 없다"는 generation을 넘을 때만
  참이다. 같은 세대 안에서는 D-058의 잠긴 행이 순서를 만든다. 비교가 불가능한 게 아니라 읽기가
  하나라 불필요한 것이었고, 위 절과 DECISIONS·BLUEPRINT·SSE_SERVER·RISK의 문장을 바로잡았다.
- **아키텍처 MEDIUM (잠재 동결):** `applied`를 `onApply` **전에** 기록했다. 렌더가 던지면 안 그린
  버전으로 다음 `since=` 읽기가 `unchanged`를 받고, `lastError`가 지워지고, 폴링이 멈춰 "실시간 연결"
  아래 낡은 보드가 남는다. 순서를 바꿨다 — 그리지 못한 것은 적용으로 치지 않아 다음 읽기가 전체
  목록을 다시 묻는다. 테스트 추가.
- **아키텍처 MEDIUM:** "프레임마다 `hub_ok`"는 거짓이다 — `change`에는 없다. 첫 구독자의 `ready`가
  허브의 첫 읽기 전에 나가 `hub_ok:false`를 실으면, heartbeat는 15초 유휴 뒤에야 오므로 바쁜 주방은
  그동안 내내 폴링했다. `change` 도착을 허브 정상의 증거로 삼는다(허브는 읽기 성공 뒤에만 보낸다).
  `ready`가 실제로 거짓을 싣는 경합 자체는 서버 테스트가 없다(아래 "하지 않은 것").
- **코드 MEDIUM:** 상태 보고마다(heartbeat·읽기 시작·끝) 보드 전체를 `innerHTML`로 다시 그렸다. 유휴
  주방에서 15초마다 카드 노드를 전부 버렸고, 쓰기 중 비활성화한 버튼을 활성화된 새 것으로 바꿨다.
  상태 보고는 상태 줄만 갱신하고 카드는 snapshot 적용에서만 다시 그린다. 울타리 테스트 추가.
- **아키텍처 MEDIUM (테스트 공백):** "삭제/취소 뒤 늦은 목록"과 "진행 PATCH와 늦은 목록 경합"에
  테스트가 없었다. 노드 테스트로 쓰기 전에 나간 읽기가 적용된 뒤 쓰기가 요청한 읽기로 수렴하는
  순서를 고정했다. 실제 브라우저는 응답을 붙들 수 없어 이 경합을 재현하지 못한다.
- **아키텍처 MEDIUM:** `SSE_SERVER.md`가 10D2를 `appliedRevision`과 `!=` 비교로 적어 둔 문장 셋과,
  `change`가 version을 싣는다는 10D1의 오래된 문장을 고쳤다. 타이머 울타리의 `auth.js` 예외를 테스트
  주석과 이 문서에 명시했다.
- **보안 LOW ×2, 코드 LOW:** `heartbeat_ms`가 없거나 0인 `ready`는 침묵 감지를 조용히 껐다 — 15초
  fallback(서버 기본값)으로 무는다. 재접속 백오프에 지터가 없어 같은 장애를 겪은 탭이 같은 tick에
  돌아왔다 — 기본값의 20%까지 **줄이는 방향으로만** 흔들어 상한을 지킨다. 테스트는 `random`을 주입한다.
- **LOW:** 브라우저 스크립트가 건너뛴 단계를 통과로 셌다 — 따로 센다. 탭 보임 행의 "읽기 한 번"은
  `ready`의 한 번을 빠뜨렸다 — 고쳤다. `ready.version`은 서버가 보내지만 화면은 쓰지 않는다(자기
  `applied.version`만 쓴다). 10D1 인계 중 "`expires_at` 만료·`id:` 부재 테스트 없음"은 닫히지 않았고
  아래에 남긴다.

## 이 단계가 하지 않은 것

- **렌더링은 여전히 문자열 조립 + `escapeHtml`이다.** 11단계가 DOM 헬퍼로 옮긴다.
- **다중 워커 전달 미측정**(10D1과 같음). 브라우저 검증은 uvicorn 1워커였다.
- **실제 프록시 경유 없음.** nginx의 비버퍼링 위치는 10A가 probe로 확인했고 이 경로는 같은 위치
  아래에 있지만, 이 화면으로 실제 nginx를 통과시키지는 않았다(BK-R039, 12A).
- **요청 제한 없음.** 12A1.
- **모바일·실기기 없음.** headless Chrome 데스크톱 한 종류다.
- **BFCache는 가짜 창에서만.** 노드 테스트는 `window`와 `document` 리스너를 한 곳에 모으고,
  브라우저 스크립트는 `visibilitychange`만 흉내 낸다. 실제 `pagehide`/`pageshow`는 12A1의 브라우저
  검증(BK-R039)으로.
- **첫 구독자의 `ready`가 `hub_ok:false`를 실을 수 있는 경합**에 서버 테스트가 없다. 화면은 다음
  `change`나 heartbeat에서 바로잡으므로 영향은 그때까지의 폴링뿐이다.
- **`expires_at` 만료·`id:` 부재**(10D1 인계)에 여전히 테스트가 없다. 서버는 `id:`를 보내지 않고
  화면은 `Last-Event-ID`를 쓰지 않으며 재접속은 새 `ready` + 전체 읽기라 동작은 맞지만, 고정되지
  않았다. 10E 또는 12A1.
