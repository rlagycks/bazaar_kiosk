# 레거시 금액과 과거 데이터 (7C)

상태: 로컬 구현과 검증. 결정은 [D-054](DECISIONS.md)(D-012 확정). 위험: BK-R007, BK-R031.
**이 단계는 어떤 값도 복원하거나 백필하지 않는다.**

## 전제부터

[D-037](DECISIONS.md)로 **운영 배포 시 보존할 과거 주문이 없다.** 빈 데이터베이스에서 시작한다.
그래서 7C는 "잃어버린 값을 되살리는" 단계가 아니다. 남은 문제는 두 가지다.

1. 스키마에는 0017 이후로 분할 수납 필드가 **비어 있을 수 있는 형태**가 남아 있고, 통계와 주문 상세가
   그 행을 해석해야 한다(BK-R007).
2. 그런 행이 몇 건이고 얼마인지 **아무도 말해 주지 않았다**(BK-R031). 운영 DB에 데이터가 발견되면
   D-037이 무효가 되는데, 발견할 방법이 없었다.

## 고친 것

| 이전 | 지금 |
| --- | --- |
| 주문 생성이 0원 항목을 `NULL`로 저장해 "모름"과 "0원"이 구분되지 않음 | 모든 금액 칸에 숫자를 넣는다(0 포함). 새 주문은 해석이 필요 없다 |
| 모호한 행이 있는지 알 방법이 없음 | `check_legacy_amounts` 명령이 건수·금액을 읽기 전용으로 보고 |
| 옛 행을 통계와 상세가 같게 읽는지 고정돼 있지 않음 | `test_legacy_reconciliation`이 세 형태를 양쪽에서 대조 |

## 점검 명령

```sh
python manage.py check_legacy_amounts          # 문장으로
python manage.py check_legacy_amounts --json   # 기계가 읽게
```

보고하는 것: 전체 주문 수, 분할 기록이 없는 주문(해석 가능한 단일 결제 / 나눌 수 없는 혼합 결제로 나눠 건수와 금액),
받은 금액이 비어 있는 주문, 합계와 분할이 어긋나는 주문과 차이 합계, 거스름돈이 기록되지 않은 주문.

**쓰지 않는다.** 집계 쿼리 하나만 돈다. 배포 전에 실행해 `needs_attention`이 거짓이면 D-037의 전제가 맞는다는
뜻이고, 참이면 값을 채우기 전에 별도 승인과 계획이 필요하다.

## 옛 행을 읽는 규칙 (바꾸지 않음)

| 형태 | 주문 상세 | 통계 |
| --- | --- | --- |
| `CASH`, 분할 없음 | 현금 = `received_amount` | 같음 |
| `TICKET`, 분할 없음 | 식권 = `received_amount` | 같음 |
| `CASH_TICKET`, 분할 없음 | 현금 0, 식권 0 (`received_amount`는 그대로 보임) | 같음 + `unattributed_orders`·`unattributed_amount`로 드러냄 |
| 거스름돈 없음 | `max(0, 현금 − max(0, 합계 − 식권))` | 같음 |

추정값을 수납 칸에 적지 않는다. 혼합 결제를 임의로 반씩 나누면 그 뒤에는 실제 기록과 구분할 수 없다.

## 검증

```sh
.venv/bin/python scripts/test_postgres.py
```

`orders/tests/test_legacy_reconciliation.py`: 새 주문의 모든 금액 칸이 숫자(0원 주문 포함), 새 DB의 점검 결과가 비어
있음, 단일 결제·혼합 결제 집계, 합계와 분할 불일치와 차이, 받은 금액·거스름돈 누락 집계, 점검이 아무것도 쓰지 않음,
명령의 문장·JSON 출력, 세 형태를 상세와 통계가 같게 읽는지 대조.

## 남은 것

- 운영 DB에 실제 데이터가 발견되면 D-037이 무효다. 그때는 이 명령의 결과를 근거로 다시 판단한다.
- 0010·0011·0015에서 삭제된 필드와 카테고리의 값은 되살릴 수 없다(BK-R031). 백업이 있으면 그것이 유일한 출처다.
- 메뉴 이름 스냅샷(D-008)은 8C와 같이 열려 있다.
