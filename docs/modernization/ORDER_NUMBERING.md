# 5단계 — 주문 번호 계약 (D-047)

상태: 구현과 로컬 브라우저 검증. BK-R003의 저장소 쪽 수정이며 운영 인수는 별도다.
디자인 변경은 없다. 주문·주방 화면에 연습 모드 안내 줄이 하나 늘었다.

## 무엇이 문제였나

번호는 PostgreSQL 시퀀스 `orders_floor_b1_seq` 하나에서 나왔다. 그래서 세 가지가 깨졌다.

1. **초기화가 없다.** 시퀀스는 날짜가 바뀌어도 계속 증가한다. 오늘 41번이면 내년 행사도
   42번부터 시작한다.
2. **연습이 진짜 번호를 쓴다.** 개발·리허설 주문이 시퀀스를 그대로 당겨서, 행사 당일의
   첫 손님이 1번을 받지 못한다. **이 서비스는 1년에 한 번 쓰기 때문에 이게 실제 피해다.**
3. **롤백해도 번호가 소비된다.** 시퀀스는 트랜잭션 밖에서 증가하므로 주문 저장이 실패해도
   번호가 사라진다. 불러서 부르는 번호에 구멍이 생긴다.

## 확정된 계약

| 항목 | 동작 |
| --- | --- |
| 진짜 번호 | 관리자 페이지에 **등록된 행사일**의 주문만 |
| 초기화 | 해마다 1번부터. 같은 해의 둘째 행사일은 이어서 증가 |
| 그 외 날짜 | 연습(`PRACTICE`) 계열의 **별도 번호대** |
| 표시 | 숫자만. 주방 화면은 연습 주문 앞에 `연습` 배지 |
| 통계 | 연습 주문은 매출·메뉴·시간대 집계에서 제외 |
| 주방 | 연습 주문도 그대로 표시 |

두 계열은 같은 날 같은 번호를 가질 수 있다. `연습 #001`과 `#001`은 다른 주문이다.

## 어떻게 고쳤나

- `EventDay` 모델과 관리자 화면을 추가했다. 운영자가 행사 날짜를 등록하는 **유일한 스위치**다.
  별도의 "연습 모드" 토글을 두지 않았다. 토글은 끄는 것을 잊으면 조용히 틀린 번호가 나간다.
- 시퀀스를 `OrderNumberCounter`(계열·연도·층) 행으로 바꿨다. 할당은 그 행을
  `select_for_update`로 잠그고 주문 생성 트랜잭션이 끝날 때까지 쥔다. 그래서 번호가
  유일하고 **롤백하면 번호가 되돌아온다.**
- 유니크 제약을 `(floor, order_date, order_no)`에서
  `(floor, number_series, EXTRACT(YEAR FROM order_date), order_no)`로 바꿨다. 연도는
  주문일에서 끌어내므로 별도 컬럼과 어긋날 수 없다.
- 카운터가 모르는 번호를 이미 가진 행이 있으면(복원·수동 입력) 충돌을 잡아 카운터를
  기존 최대값까지 올리고 다시 시도한다. 최대 5회로 제한한다.
- 할당은 트랜잭션 밖에서 호출하면 거부한다. 잠금이 곧 풀려 계약이 깨지기 때문이다.
- 0022가 `orders_floor_b1_seq`를 제거한다. 되돌리면 0020이 만들던 상태로 복원한다.
  0020의 복구 이력과 그 테스트는 그대로 둔다.
- **기존 주문이 있는 DB를 위해 두 단계를 넣었다(2026-09-18 코드 리뷰 지적).**
  새 컬럼의 기본값이 `PRACTICE`라서, 아무것도 하지 않으면 이미 기록된 주문이 전부 매출에서
  조용히 사라진다. 그래서 0022가 **번호가 있는 기존 주문을 `REAL`로 분류**한다.
  또 옛 번호는 날짜마다 1번으로 돌아갔으므로 같은 해 다른 날에 같은 번호가 있을 수 있는데,
  새 유니크는 연 단위라 그 행들이 충돌한다. 일괄 재번호는 청사진이 금지하므로,
  **마이그레이션이 충돌 행을 찾아 설명과 함께 멈춘다.** 그냥 두면
  `could not create unique index`라는 원문 오류로 깨진다(제거해서 확인했다).
  D-037은 보존할 과거 주문이 없다고 했지만, 그 결정 자체가 "데이터가 발견되면 무효"라고
  적고 있어 결정에 기대지 않고 양쪽 모두에서 옳게 동작하게 했다.

## 이 설계가 조용히 실패하는 지점

**행사일을 등록하지 않고 행사를 진행하면 모든 주문이 연습 번호로 나가고 매출에 잡히지 않는다.**
이게 가장 큰 실패 모드다. 그래서 주문·카운터·주방 화면 위에 미등록 안내 줄을 넣었다.

> 연습 모드 — 오늘(2026-09-18)은 행사일로 등록돼 있지 않습니다. 주문은 연습 번호로
> 저장되고 매출 통계에서 빠집니다.

행사 도중에 날짜를 등록해도 **이미 받은 주문은 다시 번호를 매기지 않는다.** 그 시점부터
행사 번호가 1번부터 나간다.

## 검증

| 검사 | 결과 |
| --- | --- |
| 전체 PostgreSQL 테스트 | 188개(마이그레이션20+앱168), skip0 통과 |
| `orders/tests/test_order_numbering.py` | 20개 통과(계열 선택, 연 초기화, 유일성, 충돌 복구, 롤백, 동시 할당, API, 통계 제외, 화면 경고, 관리자 등록) |
| `orders/tests/test_migration_paths.py` | 20개 통과(기존 주문 `REAL` 분류, 같은 해 번호 충돌 거부·미적용 확인, 다른 해 허용, 역방향 시퀀스 복원 포함) |
| `node --test` | 23개 통과 |
| 실제 Chromium (390×844 / 1280×900) | 12개 통과 |

브라우저 검사는 합성 DB·합성 계정·로컬 서버로 했고 운영 데이터는 쓰지 않았다.
서버·DB·볼륨은 검사 뒤 삭제했다. 검사 스크립트는 저장소 밖 작업 디렉터리에만 두었다.

**검사 자체의 신뢰성 확인:** 구현을 두 번 고의로 망가뜨려 테스트가 잡는지 봤다.

| 망가뜨린 것 | 결과 |
| --- | --- |
| `series_for`가 항상 `REAL` 반환(수정 전 동작) | 6개 실패 |
| 기존 주문 `REAL` 분류 제거 | 2개 실패 |
| 번호 충돌 사전 점검 제거 | 마이그레이션이 `could not create unique index`로 깨짐 |
| 카운터 행의 `select_for_update` 제거 | 처음에는 **통과했다.** 유니크 제약이 충돌을 잡아 재시도로 번호가 갈렸기 때문이다. 테스트가 충돌 복구 호출을 감시하도록 고치고, 카운터 행이 이미 있는 상태에서 경합하게 바꾼 뒤에야 실패했다 |

두 번째가 중요하다. **결과만 보면 락 없는 구현도 옳아 보였다.** 경합이 정상 경로로
처리됐는지까지 확인해야 락의 존재를 증명한다.

## 남은 것

- 대시보드 기간이 아직 `2025-10-18`로 고정돼 있다. 이번 범위가 아니고 **D-013**이다.
  행사일 등록이 생겼으므로 그 결정에서 "최근 행사일" 같은 선택지를 함께 본다.
- 취소 주문 제외는 이미 상태 필터로 동작한다(D-048의 해당 항목). 부족 결제 거부와
  거스름돈 저장은 6A/6B/7A다.
- 카운터의 오늘 메뉴별 집계(`stats_menu_counts`)는 **오늘의 계열을 따른다.** 행사일이면
  행사 주문을, 연습일이면 연습 주문을 센다. 매출 보고가 아니라 진행 중인 현황이라서
  연습 중에도 쓸모 있어야 하고, 두 계열이 섞이지는 않는다. 매출 집계는 그대로 행사 계열만 본다.
- 층은 `B1` 하나뿐이지만 카운터는 층별로 센다. 층이 늘어도 번호가 섞이지 않는다.
- **관리자 화면 접근 정책이 없다(2026-09-18 보안 리뷰 지적).** 행사일 등록은 이제 그 해 매출이
  집계되는지를 가르는 통제인데, 지키는 것은 Django 기본 `is_staff`/`is_superuser`뿐이다.
  역할 계정 로그인에는 기기 바인딩·실패 잠금 정책(D-045)이 있지만 `/admin/`에는 계정 발급·
  잠금·감사 정책이 정해져 있지 않다. 관리자 계정이 공유되거나 탈취되면 행사일 등록을
  지우는 것만으로 한 행사의 매출 기록을 조용히 0으로 만들 수 있다. D-011 범위에 넣거나
  별도 결정으로 다룬다. 이번 단계에서 새로 생긴 위험이 아니라 이번 단계로 **무거워진** 위험이다.
- BK-R003은 저장소에서 닫혔고 운영 인수 전까지 Open이다.
