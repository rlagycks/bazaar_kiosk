# 6B — 상태 전이와 포장 번호 (D-050)

상태: 구현과 로컬 브라우저 검증. BK-R013의 저장소 쪽 수정이며 운영 인수는 별도다.
화면 구성은 그대로다. 달라진 것은 거부되는 동작이 생겼다는 점이다.

## 2026-09-22 개정 — UI-05B / D-063

아래는 6B 당시 이력이다. 현재는 **수량 충족만으로 READY가 되지 않는다**. 명시적인
모니터링 출발 확인이 수량·READY·출발 시각을 함께 기록한다. 준비 수량을 줄이면
READY→PREPARING으로 돌아가고 출발 시각을 지운다. 기존 완료 이력에는 출발 시각을
추정하지 않는다. 일반 상태 API의 READY는 출발 기록을 만들지 않는다.
취소 최종·전체 취소·포장 번호 점유는 유지한다. [현재 계약](UI_MONITORING.md)을 따른다.

## 무엇이 문제였나

**1. 취소가 취소가 아니었다.** 상태 엔드포인트는 받은 값을 그대로 저장했다.
취소된 주문에 `PREPARING`을 보내면 200과 함께 되살아났다.

**2. 두 writer가 서로 다른 규칙을 썼다.** 조리 진행 엔드포인트는 취소된 주문을 거부했는데,
상태 엔드포인트는 되살렸다. 같은 주문에 대해 한쪽은 "끝났다", 한쪽은 "계속할 수 있다"고 했다.

**3. 아무도 주문을 잠그지 않았다.** 취소와 조리 진행이 동시에 오면 나중 쓰기가 이겼다.
취소가 조용히 사라질 수 있었다.

**4. 포장 번호표가 겹칠 수 있었다.** 101~120 번호에 아무 제한이 없어서, 손님 두 명이
같은 105번 표를 들고 서 있어도 서버는 막지 않았다.

## 확정된 계약 (D-050)

```
PREPARING ──> READY, CANCELLED
READY     ──> PREPARING, CANCELLED
CANCELLED ──> (없음)
```

| 항목 | 동작 | 정한 사람 |
| --- | --- | --- |
| 취소 되살리기 | 불가. **취소는 최종** | 사용자 |
| 완료 → 준비중 | 허용 | 사용자 |
| 사용 중인 포장 번호 | 거부(409) | 사용자 |
| 완료(READY) 주문의 취소 | 허용 | 에이전트 |
| 같은 상태로 다시 보내기 | 200, 아무 일도 하지 않음 | 에이전트 |
| 금지된 전이 | 409 (형식 오류는 400 그대로) | 에이전트 |
| 취소된 주문의 조리 진행 | 409 (기존 400에서 변경) | 에이전트 |
| 직접 상태 vs 품목 수량 | 수량이 바뀌면 수량이 이긴다 | 에이전트 |
| 홀 테이블 번호 | 중복 허용(현행 유지) | 에이전트 |

**취소가 최종인 대가:** 잘못 취소하면 새 주문을 받아야 하고 번호가 하나 늘어난다.
**포장 번호 거부의 대가:** 번호표가 다 나가면 주문을 받지 못한다.
둘 다 질문과 함께 제시했고 사용자가 그 조건으로 골랐다.

## 어떻게 고쳤나

- `orders/services/status.py` 하나로 모았다. 전이표가 여기 있고, 두 엔드포인트가 모두 여기를 지난다.
- 상태 변경은 **주문 행을 잠그고** 읽기와 쓰기를 한 단계로 만든다. 잠그지 않으면 두 요청이
  모두 `PREPARING`을 읽고 나중 쓰기가 이긴다. 취소가 사라지던 경로다.
- 조리 진행은 **주문을 먼저 잠그고 그다음 품목을 잠근다.** 상태 판단은 주문의 것이고,
  그 사이에 취소가 끼어들면 안 된다. 순서를 어디서나 같게 두는 것은 같은 주문의 두 요청이
  서로를 기다리다 교착하지 않게 하기 위해서다(2026-09-18 보안 리뷰 지적).
- 포장 번호는 **부분 유니크 제약**으로 막는다.
  `UNIQUE(table) WHERE order_type='TAKEOUT' AND status IN ('PREPARING','READY')`.
  뷰에서 미리 확인해 문장으로 답하지만, **경계 자체는 DB에 있다.** 동시에 두 요청이
  확인하면 둘 다 비어 있다고 보기 때문이다.
- 주문 화면은 409 응답의 `detail`만 꺼내 보여준다. 고치기 전에는 JSON 원문이 그대로
  경고창에 떴다.

둘 다 비어 있다.

## 남은 것

- 관리자 화면에서 상태를 바꾸면 이 전이표를 지나지 않는다. **7B 범위**이며 D-011과 묶인다.
- 홀+포장이 섞인 주문의 분류는 이번에 정하지 않았다(D-014의 남은 부분). 현행 유지다.
- 번호표를 회수했는데 주문이 READY로 남아 있으면 번호가 계속 묶인다. "전달 완료" 상태는
  지금 없고, 상태를 늘리는 것은 청사진이 금지한다. 필요해지면 별도 결정이다.
- **묶인 번호를 푸는 사람은 주방뿐이다(2026-09-18 보안 리뷰 지적).** 취소는 주방 계정만
  할 수 있다(D-040). 주문 계정이 잘못된 번호로 주문을 넣으면 스스로 되돌릴 수 없고 주방이
  취소해 줘야 한다. 20개가 전부 묶이면 포장 주문을 받지 못한다. 현장에서 주방과 카운터가
  같은 자리에 있다는 전제에 기대고 있으며, 그 전제가 깨지면 권한을 다시 봐야 한다(D-003/D-040).
- BK-R013은 저장소에서 닫혔고 운영 인수 전까지 Open이다.
- **0024 적용 전 점검(2026-09-20 DB 리뷰 반영).** 운영 DB에 같은 포장 번호를 쥔 활성 포장 주문이
  둘 이상 있으면 마이그레이션은 `23505 uq_active_takeout_slot`로 **멈추고 아무 행도 바꾸지 않는다**
  (전용 PG에서 재현·회귀 고정: `test_migration_paths`의 0023→0024 두 사례). 배포 절차에서
  먼저 아래 조회를 실행하고, 결과가 있으면 해당 주문을 취소하거나 전달 완료 처리한 뒤 다시 적용한다.

  ```sql
  SELECT table_id, count(*) FROM orders_order
   WHERE order_type = 'TAKEOUT' AND status IN ('PREPARING', 'READY')
   GROUP BY table_id HAVING count(*) > 1;
  ```
- **적용 시점.** 0024는 부분 유니크 인덱스를 트랜잭션 안에서 만들므로 그동안 `orders_order`에
  ACCESS EXCLUSIVE 잠금이 걸린다. 행사 규모에서는 순간이지만, 주문이 몰리는 시간이 아니라
  **행사 시작 전**에 적용한다(2026-09-20 코드 리뷰).
- **같은 요청의 재전송이 포장 번호 충돌과 겹치는 경우(2026-09-20 코드 리뷰, HIGH → 수정).**
  같은 `request_id`를 가진 두 요청이 동시에 도착하면 둘 다 replay 조회를 통과해 삽입에 이르고,
  진 쪽은 이긴 쪽(자기 자신의 첫 도착)이 쥔 번호 때문에 `uq_active_takeout_slot`에 걸린다.
  수정 전에는 이를 "다른 번호를 쓰라"는 409로 답해 봉사자가 106번으로 다시 저장하게 만들었다.
  이제 IntegrityError를 받으면 어느 인덱스가 거부했든 먼저 요청 ID를 다시 조회해 같은 시도면
  그 주문을 200으로 돌려주고, 다른 시도일 때만 409를 낸다.
  회귀: `test_a_retry_of_the_same_attempt_racing_itself_gets_its_own_order_back` (수정 전 201/409, 후 200/201).
- `sync_from_items`도 `change()`를 지나 전이표가 한 곳에만 있도록 했다(리뷰 MEDIUM).
- 화면에 `detail`이 보이는지 확인하는 두 테스트는 템플릿 문자열 존재만 본다(리뷰 MEDIUM).
  실제 표시는 2026-09-18 Chromium 수동 검증에 기대며, 화면 JS 단위 테스트는 11(UI 정리)에 남긴다.
