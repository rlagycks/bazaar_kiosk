# 결제 검증과 금액 의미 (7A)

상태: 로컬 구현과 검증. 결정 근거는 [D-048](DECISIONS.md)(D-005 확정)이고, 레거시 필드 정합(D-012)은
건드리지 않았다(7C). 위험: BK-R014, BK-R030.

## 고친 것

| 이전(4A4까지) | 지금 |
| --- | --- |
| 금액을 `int()`로 받아 `True`→1원, `1.9`→1원으로 잘림 | 정수 또는 숫자 문자열만. float·bool·소수 문자열·음수·상한 초과는 400 |
| 5000원 주문에 0원·4999원 수납도 201 | 받은 금액 < 합계면 **400, 아무것도 저장하지 않음** |
| 금액·수량·합계에 상한 없음 | 금액 한 칸 1,000만 원, 합계 1,000만 원, 수량 99 |
| 거스름돈은 조회 때마다 계산 | 생성 시 서버가 정해 `Order.change_amount`에 저장(0026) |
| 화면은 식권 초과분도 거스름돈으로 표시 | 화면과 서버가 같은 규칙 |

합계는 전과 같이 서버의 메뉴 가격 스냅샷 × 수량이다. 클라이언트가 보낸 `total_price`는 무시된다.

## 규칙 (orders/services/payments.py)

- `parse_amount(raw, field)`: `None`·빈 문자열은 "보내지 않음"(None). 정수(bool 제외)나 숫자 문자열(콤마·공백 허용)만
  받는다. `5000.0`도 거부한다. 돈을 반올림하는 코드는 두지 않는다.
- `read_payment(payload)`: CASH·TICKET은 `received_amount` 한 값, 없으면 0. CASH_TICKET은 두 필드 또는
  옛 화면의 `"현금+식권"` 문자열이며 **둘 다 0보다 커야** 한다.
- `order_total(lines)`: 단가 × 수량 합. 상한 초과면 거부.
- `settle(payment, total)`: `received < total`이면 `PaymentRefused`("받은 금액이 합계보다 적습니다").
  거스름돈 = `max(0, cash - max(0, total - ticket))`.

**에이전트 판단(뒤집을 수 있음):** 식권 초과분은 거스름돈이 아니다. 식권을 현금으로 돌려주지 않는다는 뜻이며,
4A4 이전 `_serialize_order`가 이미 그렇게 계산하고 있었다. D-048은 "거스름돈을 저장한다"만 정했고 식권
거스름돈은 정하지 않았다. 상한 세 값(1,000만 원·99개)도 에이전트가 정했다.

## 예시 (합계 5,000원)

| 결제 | 결과 | 저장되는 거스름돈 |
| --- | --- | --- |
| 현금 5,000 | 201 | 0 |
| 현금 10,000 | 201 | 5,000 |
| 현금 4,999 / 0 / 없음 | 400 | (저장 없음) |
| 식권 6,000 | 201 | 0 |
| 식권 4,000 | 400 | |
| 현금 3,000 + 식권 3,000 | 201 | 1,000 |
| 현금 1,000 + 식권 6,000 | 201 | 1,000 |
| 현금 2,000 + 식권 2,000 | 400 | |
| 현금 5,000, 식권 0 (혼합) | 400 "현금과 식권 금액을 모두 입력하세요." | |
| 현금 `1.5`·`true`·`-1`·`"abc"`·`10^9` | 400 | |

## 스키마

0026 `orders.Order.change_amount` (nullable PositiveIntegerField). 추가만 한다. 이전 행은 NULL이고 API가 옛
방식으로 계산해 보여준다. 원본 수납 필드(`received_*`)는 덮어쓰지 않는다(7C).

롤백: 0026 역적용은 열 삭제뿐이다. 이전 앱은 이 열을 모르므로 새 스키마 위에서도 동작한다.
