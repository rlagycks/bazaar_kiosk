# 현대화 작업 제어 센터

이 디렉터리는 Bazaar Kiosk 현대화 작업의 인수인계 중심입니다.
검증된 사실, 결정 대기 사항, 단계 경계 및 세션 프롬프트를 분리해 보관하므로 새 세션에서
이력을 재구성하지 않고 작업을 재개할 수 있습니다.

## 현재 작업 재개

**2026-09-23 최신 (포장 교환권, D-069):** 포장은 교환권 방식으로 바뀌어 번호표 필수·점유 규칙을 뺐다(0031).
포장만 주문은 테이블 없이 접수하고 주문 번호가 교환권이다. [이슈 #87](https://github.com/rlagycks/bazaar_kiosk/issues/87),
브랜치 `phase-10g-takeout-voucher`. 10E 결정 항목 중 목표 수치(D-067 제안 채택)·워커 재시작 유예 10 s 유지(행사 중 배포 금지)는
확정, 보고서는 로컬 브랜치에만 둔다.

**2026-09-22 최신 (UI-05C 제출):** 모니터링 UI-05B는 [PR82](https://github.com/rlagycks/bazaar_kiosk/pull/82)로

구현·검증했다(D-064). 머지된 develop `e61d6ab`를 기준으로 통계 변경만 [PR83](https://github.com/rlagycks/bazaar_kiosk/pull/83)에 제출했다.

10E 부하·단계11의 잔여 인수·12 운영 인수는 남아 있다.

**2026-09-21 (UI-05A 이력):** 사용자가 **05안 채택과 코드 반영**을 지시했다(D-062).
[UI 적용 계획](UI_IMPLEMENTATION.md)에 따라 로그인·내 메뉴·휴대폰 주문/결제를 첫 단계로
구현한다. 모니터링의 “완료=서빙 출발”은 서버 상태 전이와 함께 UI-05B에서 다룬다.
누적·통계는 UI-05C, 10E 부하·12 운영 인수는 별도다. 아래는 이전 단계의 기록이다.

**2026-09-21 (10D2):** [주방 보드를 스트림에 붙였다](KITCHEN_CLIENT.md)(D-061). 4B2 이후 수동이던
보드가 다시 스스로 갱신된다. 사용자가 **5초 후퇴 폴링**과 **보이는 탭만 연결**을 골랐다. 읽는 시점을
정하는 곳은 스케줄러 하나이고 폴링은 D-019 그대로 "스트림 open + `hub_ok` + 완전한 snapshot"일 때만
멈춘다 — heartbeat는 증거가 아니다. 목록·단건 두 경로를 snapshot 하나로 줄여 BK-R033의 경합이 막을
것 없이 사라졌고, 응답 역전은 순서 없는 버전 대신 epoch으로 막는다. 브라우저 브리지가 없어 로컬
Chrome을 headless로 직접 구동해 17건을 확인했다: 다른 연결의 커밋이 0.6~1.7초, 서버 SIGKILL 뒤 복구
3.1초, 회수 뒤 로그인 0.5초. 다음은 10E(부하) 또는 11(UI 정리).

**2026-09-21 (10D1):** [주방의 이벤트 스트림](SSE_SERVER.md)을 세웠다(D-060). 이제 서버가
화면에 먼저 말한다. 요청은 한 번 인가되고 끝나지만 스트림은 저녁 내내 열려 있어서, 사용자가
**이벤트마다 재인가**를 골랐고 묶음 조회로 감당한다 — 로그아웃한 기기는 다음 이벤트에서 멈춘다.
허브는 scope별로 실제 보이는 것을 비교해 **포장 화면을 홀 변경으로 깨우지 않는다**(깨운 비율
100%→67%). 테스트가 설계 오류를 하나 고쳤다: 허브가 DB를 못 읽을 때 스트림을 끊으면 재접속
루프가 되므로, 끊지 않고 `hub_ok: false`를 싣는다. 화면이 붙는 것은 10D2다.

**2026-09-20 (10C):** [버전과 일치하는 snapshot](SNAPSHOT.md)을 만들었다(D-059).
10B의 숫자가 이제 **어떤 데이터와 짝인지** 말할 수 있다. 사용자가 **REPEATABLE READ 트랜잭션
하나**를 골랐고, 그래서 표시와 주문이 한 시점에서 읽힌다 — 두 문장으로 읽으면 화면이 자기가
보여 주는 것보다 앞선 버전을 저장해 영구히 낡은 채로 남는다. 버전은 `generation:value:scope`이고
크기를 재는 게 아니라 비교한다: 복원된 카운터가 화면이 쥔 값에 다시 도달해도 "안 바뀜"을
답하지 못하고, 권한이 바뀐 계정의 옛 커서도 거부된다. 읽기 증폭은 변경당 폴 1회·3회로 쟀고
1:3에서 **폴 3개 중 1개만 재조회**·중앙값 1ms다 — 전역 1행을 유지한다. 리뷰가 제가 쓴 근거
다섯 개를 반증했고(특히 "중첩돼도 잃는 게 없다"는 READ COMMITTED에서 거짓이다) 전부 고쳐
적었다. 화면이 이걸 부르는 건 10D2다.

**2026-09-20 (10B):** [모든 writer의 변경 감지](CHANGE_DETECTION.md)를 세웠다(D-058).
주방 보드가 자기가 낡았는지 물을 수 있는 숫자가 처음으로 생겼다. 사용자가 **최신 상태 수렴**과
**서비스 계층 통합**을 골랐고, writer 전수 조사가 설계를 두 번 바꿨다 — 조리 진행은 뷰 안에서
저장되고 상태가 안 바뀔 때가 있으며, 행사일 등록은 주문 행을 하나도 쓰지 않고 모든 주문의
배지를 바꾼다. 숫자는 잠긴 행에서 커밋 순서대로 나온다. 아직 화면은 이걸 읽지 않는다(10C/10D1).

**2026-09-20 (10A):** [ASGI 실행과 프록시](ASGI_RUNTIME.md)를 실제로 증명했다(D-057).
운영 실행이 WSGI였으므로 SSE는 스트리밍 자체가 불가능했다. 이제 uvicorn 워커 3개로 돌고,
동기 전용이던 WhiteNoise 미들웨어를 빼 정적 파일은 프록시가 낸다. 실제 스택에서 프레임이
하나씩 도착하고, 스트림 48개를 열어 둬도 일반 API 중앙값은 19~22ms로 변하지 않는다.
측정은 `scripts/stream_smoke.py`로 재현한다. 스트림 1개는 요청당 스레드 1개를 쓰며
이건 구조적이라 없앨 수 없다. 이 probe에서 DB 연결이 1로 고정인 것은 뷰가 연결을 먼저
놓기 때문이고, 이벤트마다 DB를 읽는 10D1에는 그대로 적용되지 않는다.

**2026-09-20 (9):** [API 입력 계약과 경계](API_CONTRACTS.md)를 정리했다. 잘못된 입력이 내던 500 36건이 0건이 됐고,

- `검증됨(Verified)`은 명령, 코드 위치 또는 재현 가능한 관찰 결과가 해당 내용을 뒷받침한다는
  의미입니다.
- `가설(Hypothesis)`은 위험에 개연성이 있지만 집중적인 재현이나 운영 환경 확인이 필요하다는
  의미입니다.
- `결정 대기(Pending decision)`는 구현 과정에서 사용자를 대신해 암묵적으로 선택해서는 안 된다는
  의미입니다.

사실을 다시 확인하면 `마지막 검증` 필드를 업데이트합니다. 이전 항목과 근거를 보존하지
않은 채 중요한 결정을 덮어쓰지 마세요.
