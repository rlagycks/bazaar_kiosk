# 현대화 작업 제어 센터

이 디렉터리는 Bazaar Kiosk 현대화 작업의 인수인계 중심입니다.
검증된 사실, 결정 대기 사항, 단계 경계 및 세션 프롬프트를 분리해 보관하므로 새 세션에서
이력을 재구성하지 않고 작업을 재개할 수 있습니다.

## 현재 작업 재개

**2026-09-20 최신 (4B2):** [브라우저의 외부 Realtime을 제거](EXTERNAL_REALTIME_REMOVAL.md)했다(D-056). 사용자 지시로
폴링도 함께 없앴으므로 자체 SSE(10D)까지 주방 보드는 수동 갱신이며 화면이 그렇게 표시한다. 외부 설정 정리는 인계 목록이다.

**2026-09-20 (8B):** [주방 대기 목록](KITCHEN_QUEUE.md)은 오래된 순으로 전부 돌려주고, 잘리면 남은 건수를
밝힌다(D-055). 테이블·메뉴 캐시를 제거해 관리자의 비활성화가 모든 워커에 즉시 반영된다.

**2026-09-20 (7C):** [레거시 금액](LEGACY_AMOUNTS.md)은 원본을 그대로 두고 점검 명령으로 드러낸다(D-054).
새 주문은 모든 금액 칸에 숫자를 저장한다. 백필 마이그레이션은 없다.

**2026-09-20 (8C):** [매출 보고](REPORTING.md)의 기간과 금액 의미를 확정했다(D-053). 기본 기간은 가장 최근
행사일이고, 취소 제외·순현금·메뉴 ID 집계를 보여 준다. 화면에서 기간을 고를 수 있다.

**2026-09-20 (7B):** [관리자 주문 편집](ADMIN_EDITS.md)을 서비스 경유로 바꿨다(D-052). 품목 편집 시 합계·거스름돈
재계산과 이력, 단가·번호·수납 읽기 전용, 상태는 주방 전이표. 다음 후보는 7C 또는 8C.

**2026-09-20 (7A):** [서버 결제 검증](PAYMENTS.md)을 로컬 구현했다. 금액·수량·합계 검증, 부족 결제 400 거부,
거스름돈 저장(0026). 주문 생성 POST는 서빙 한정(PR #68). 다음 후보는 7B(관리자 쓰기) 또는 8C.

**2026-09-20 (4A4):** [개인 계정·권한 4종·행위자 기록](ACCOUNTS.md)을 로컬 구현했다.
이름 + 행사 공용 비밀번호 로그인, 관리자 화면의 계정·권한 등록, 포장/식당 서버 경계, 주문 생성자와
상태·조리 진행 이력. `ROLE_ACCOUNTS`는 `EVENT_PASSWORD_HASH`로 대체됐다. 운영 배포는 하지 않았다.

**2026-09-19 기획 변경:** [D-051](DECISIONS.md)로 인증 주체를 개인 계정(이름 + 행사 공용 비밀번호)과
권한 4종(서빙·식당 모니터링·포장 모니터링·누적+통계)으로 바꾸기로 했다. JWT·자동 갱신 구조는 유지한다.
구현은 새 단계 [4A4](BLUEPRINT.md#phase-4a4)이며 6B PR 이후, 7A 이전이다.

**2026-09-15 최신:** [JWT 인증](JWT_AUTHENTICATION.md)을 로컬 구현했습니다.
ID/비밀번호 환경 설정, 디바이스별 갱신·폐기, API Bearer 검증과 화면 session 결속을 포함합니다.
**2026-09-18 (2):** 4B1로 [주문·카운터 화면의 안전한 렌더링](CONTENT_SECURITY.md)을 구현했습니다.
메뉴 이름에 든 스크립트가 실행되던 것을 브라우저로 재현하고 닫았습니다. 표시도 함께 고쳐져
`A&W <cola>` 같은 정상 이름이 더는 깨지지 않습니다.

**2026-09-18:** 4A3으로 [배포 후보 구성](DEPLOYMENT_CANDIDATE.md)을 만들었습니다.
Compose 한 스택, 파일로 전달하는 비밀값, 프록시만 노출, 단일 DB 역할과 권한 축소,
프록시 뒤 클라이언트 주소 신뢰 경계(이슈 #61)입니다. 실제 배포는 하지 않았습니다.

**2026-09-17:** 남은 정책을 [D-045](DECISIONS.md)로 확정했습니다. 비밀번호 변경 시 전체 디바이스 종료,
계정 ID+접속 IP별 5분 10회 실패 시 5분 잠금(코드 고정, 환경 변수 아님), 메뉴·테이블 조회는
인증된 세 계정입니다. 운영 배포와 실제 자격증명 공급은 하지 않았습니다.
[SESSION_SETUP](SESSION_SETUP.md)에서 현재 인수인계 상태를 확인합니다.

## 문서 상태

- `검증됨(Verified)`은 명령, 코드 위치 또는 재현 가능한 관찰 결과가 해당 내용을 뒷받침한다는
  의미입니다.
- `가설(Hypothesis)`은 위험에 개연성이 있지만 집중적인 재현이나 운영 환경 확인이 필요하다는
  의미입니다.
- `결정 대기(Pending decision)`는 구현 과정에서 사용자를 대신해 암묵적으로 선택해서는 안 된다는
  의미입니다.

사실을 다시 확인하면 `마지막 검증` 필드를 업데이트합니다. 이전 항목과 근거를 보존하지
않은 채 중요한 결정을 덮어쓰지 마세요.

## 과거 프롬프트 설계 출처

초기 세션 지침은 2026-09-06 당시 기록한 공식
[GPT-6 Astra 모델 가이드](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra)를
바탕으로 작성했습니다. 특히 가이드에서 조정 가능한 Astra 동작으로 언급한 주도성, 지침
우선순위, 작성 방식, 위임 및 테스트 비례성을 프롬프트에 명시적으로 정의했습니다.

프롬프트는 가이드를 그대로 복사하지 않고 바꾸어 표현했습니다. 기능과 호환성은 변경될 수
있으므로 모델/API 매개변수를 변경하기 전에 공식 페이지를 다시 확인하세요.

이 출처는 초기 설계 기록입니다. 현재 실행 계약은 모델에 공통이며 모델 선택·API 설정을 강제하지 않습니다.
