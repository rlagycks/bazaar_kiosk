# 4A1 잔여 — 운영 필수 설정 누락 시 시작 거부

2026-09-14 · [이슈 #57](https://github.com/rlagycks/bazaar_kiosk/issues/57) ·
[BK-R028](ANALYSIS_REPORT.md#bk-r028)·[BK-R002](ANALYSIS_REPORT.md#bk-r002) ·
단계 [4A1](BLUEPRINT.md#phase-4a1) · 결정 [D-039](DECISIONS.md).

## 무엇을 고쳤는가

설정이 없으면 조용히 기본값으로 대체됐다. `SECRET_KEY`는 `dev-only-not-for-prod`,
`ROLE_PINS`는 이 저장소에 그대로 적혀 있는 다섯 개 PIN이었다.
즉 환경 변수를 하나도 넣지 않은 배포가 **공개된 자격증명으로 정상 기동**했다.
BK-R002와 BK-R028이 지목한 것이 이것이다.

이제 운영 모드에서 필수값이 없거나 저장소에 적힌 기본값 그대로면 시작을 거부한다.

## DEBUG에 기본값을 두지 않는 이유

D-039는 "운영 필수 설정이 없으면 거부한다"고 정했다. 그런데 운영 여부를 `DEBUG`로 판정하고
그 `DEBUG`가 기본 켜짐이면, **아무것도 설정하지 않은 배포는 검사에 아예 닿지 않는다.**
개발 설정 그대로 뜨고 `ALLOWED_HOSTS`는 `['*']`가 되며 거부는 장식이 된다.

그래서 `DEBUG`는 `0` 또는 `1`을 명시해야 한다. 기본값이 없다.
`.env.example`에 이미 들어 있으므로 문서화된 개발 절차는 그대로 동작한다.

이 판단은 D-039의 문장을 넘어선 것이 아니라 그 문장이 실효를 갖게 하는 조건이다.
같은 종류의 실수를 단계3에서 한 번 했다. 매출 통계를 카운터 전용으로 막아 두고
같은 숫자가 나가는 주문 조회를 열어 둔 것이다. 막았다고 적혀 있는데 막히지 않는 상태다.

## 검사 내용

운영(`DEBUG=0`)에서 아래가 없거나 저장소 기본값이면 `ImproperlyConfigured`로 멈춘다.

| 설정 | 거부 조건 |
| --- | --- |
| `SECRET_KEY` | 미설정이거나 `dev-only-not-for-prod` |
| `ALLOWED_HOSTS` | 비어 있음 |
| `CSRF_TRUSTED_ORIGINS` | 비어 있음 |
| `ROLE_PINS` | 미설정이거나 저장소에 공개된 시연용 다섯 개 그대로이거나 파싱 결과가 빈 값 |

`DATABASE_URL`은 모드와 무관하게 이전부터 필수다. PostgreSQL이 아니면 시작하지 않는다(D-029).

**미설정과 "저장소에 적힌 값 그대로"는 같은 실패로 다룬다.** 존재 여부만 보면
`.env.example`을 그대로 복사한 배포가 통과한다. 그것이 정확히 막으려던 상황이다.

**거부 메시지는 환경 변수 이름만 말하고 값은 절대 넣지 않는다.** 이 예외는 오류 보고에
도달할 수 있고, 값은 BK-R028이 거기 나타나면 안 된다고 한 바로 그것이다.
누락된 항목은 한 번에 모두 보고한다. 하나씩 알려주면 새 배포가 재시작과 수정을 반복하게 된다.

개발(`DEBUG=1`)은 영향이 없다. 아무것도 설정하지 않아도 그대로 뜬다.

## 예시 파일

`.env.example`은 이미 있었으므로 새로 만들지 않고 확장했다(D-039).
항목마다 `[필수]`·`[생성]`·`[입력]`·`[선택]`을 표시했다.
`[생성]`은 사람이 정할 필요 없이 만들어 쓰면 되는 값이며 생성 명령을 파일에 적었다.

**실제 비밀값은 저장소에 넣지 않는다.** 예시 파일에는 자리 표시자만 있고,
만든 값은 이 파일이 아니라 운영 환경의 비밀 저장소에 넣으라고 명시했다.

4A2에서 쓸 JWT 항목도 자리만 만들어 두었고 **필수로 만들지 않았다.**
읽는 코드가 아직 없는데 필수로 걸면 쓰이지도 않는 값 때문에 시작이 막힌다.

아래 거부들이 검사 때문인지 탐침 자체의 오류인지 구분할 수 없다.
필수 항목은 하나씩 따로 비워서 확인한다. 묶어서 비우면 어느 것이 실제로 강제되는지 알 수 없다.

## 같이 고친 것

`settings_test_pg`가 기본 설정을 별표 import 하면서 환경을 비우므로 `DEBUG=1`을 명시하게 했다.
이 프로파일은 바로 아래에서 `DEBUG=False`를 고정하고 배포로 동작하지 않는다.
배포 관문 자체는 위 회귀가 실제 설정 모듈을 새 프로세스에서 띄워 검사한다.

`test_database_config`의 탐침도 `DEBUG`를 명시하게 했다. 그리고 **거부 사유가
`DATABASE_URL`인지 단언하도록 좁혔다.** 그러지 않으면 URL과 무관한 어떤 거부라도
통과로 보인다. 실제로 이 변경 직후 그 테스트가 잘못된 이유로 통과할 수 있는 상태였다.

## 남는 경계

**이것으로 BK-R028이 종료되지 않는다.** 저장소에서 기본값 대체를 막았을 뿐
운영 환경에 실제로 어떤 값이 들어가는지는 확인하지 않았다. 운영 인수가 남는다.

**BK-R002도 종료되지 않는다.** PIN을 바꾸도록 강제했을 뿐 인증 방식은 그대로다.
4자리 PIN에 시도 제한이 없고 공용 계정이라는 성질은 4A2의 D-035 전환에서 다룬다.

`DEBUG=0`에서만 검사하므로, 운영 환경이 실수로 `DEBUG=1`을 넣으면 검사는 지나간다.
`DEBUG=1` 자체를 운영에서 막는 것은 배포 프로필이 확정되는 4A3의 `check --deploy` 범위다.
