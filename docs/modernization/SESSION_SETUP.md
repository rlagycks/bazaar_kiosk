# 현대화 세션 시작과 인수인계

마지막 상태 정리: 2026-09-15. 이 문서는 모델에 공통인 작업 계약이다.

## 현재 단계와 기준

- **2026-09-15 D-034 단일화:** 로그인 역할은 `ORDER`·`B1_COUNTER`·`KITCHEN` 세 개다.
  주방 전체·홀·포장 URL과 `ALL`·`HALL`·`TAKEOUT` 필터는 유지하고 모두 `KITCHEN`으로 접근한다.
  삭제된 `KITCHEN_HALL`·`KITCHEN_TAKEOUT` 로그인과 기존 세션은 거부하며 자동 변환하지 않는다.
  기존 `ROLE_PINS`에서 두 항목을 제거하고 재시작한 뒤 `KITCHEN`으로 다시 로그인한다.
  운영 설정에 삭제된 역할이 남으면 시작을 거부한다. 인증 방식은 여전히 PIN 세션이다.

- **2026-09-14에 4A2를 착수했다.** `auth.py`를 `orders/roles.py`(역할 이름)·
  `orders/views/guards.py`(인가 가드·`csrf_failure`)·`orders/views/auth.py`(로그인 흐름)로 나눴다.
  GET 로그아웃을 닫았고(POST 전용) 자격증명 회수가 기존 세션에 닿게 했다(`provisioned_roles()`).
  **JWT 발급·리프레시·기기 결속은 시작하지 않았다.** 다음 독립 구현 범위이며,
  합성 자격증명으로 로컬 구현·검증할 수 있다. 실제 id/password는 운영 계정 설정에 필요하다.
  회수는 됐지만 **교체(PIN 값 변경)는 기존 세션을 끊지 않는다.** 그 방식은 미결이다.
  회수에는 **재시작이 필요하다.** 바뀐 것은 재시작이 그 역할만 끊는다는 점이다(예전엔 전원).
  D-039의 부팅 게이트가 역할 다섯 개를 전부 요구해 회수가 배포 불가능했던 것을 함께 고쳤다.
  D-043으로 `SameSite`=Strict 와 리프레시 CSRF 토큰 방어를 정했는데 **에이전트 판단이다.**
- **2026-09-14에 4A1 잔여 구현과 4A2 설계 확정을 진행했다.**
  운영 필수 설정이 없거나 저장소 기본값이면 시작을 거부한다(D-039).
  `DEBUG`는 명시해야 하며 기본값이 없다. [구현과 증거](REQUIRED_SETTINGS.md).
  **BK-R028·BK-R002는 종료되지 않았다.** 운영 실제 값은 미확인이고 인증 방식도 그대로다.
  D-042로 4A2 설계를 확정했다. `httpOnly` 쿠키 리프레시 토큰, 기기별 토큰 분리,
  액세스15분·리프레시12시간, 401/403 분리다. **설계만이며 인증 코드는 변경하지 않았다.**
  `.env.example`의 JWT 항목은 자리 표시자이고 코드가 아직 읽지 않는다.
- **2026-09-13에 단계3 API 인가 구현까지 진행했다.**
  익명은 모든 API에서 차단되고 상태 변경·조리 진행은 주방, 매출 조회는 주방 카운터다.
  주문 조회는 주방·카운터이고 주문 생성은 인증된 전 계정이다. [구현과 증거](API_AUTHORIZATION.md).
  BK-R001은 Repo-fixed다. 다만 1차 구현은 조회를 열어 두어 매출 제한이 무효였고
  독립 리뷰가 찾아 D-040 2차 개정으로 좁혔다. D-041로 세션 고정과 CSRF 거부 형식도 닫았다.
  3차 리뷰가 찾은 집계 우회는 `kitchen-menu-summary` 경로를 제거해 닫았다. 호출하는 화면이 없었다.
  **인증 방식은 바꾸지 않았다.** 여전히 공용 PIN 세션이며 D-035의 JWT 전환은 4A2다.
  선행 측정은 [권한 현황](AUTHORIZATION_MATRIX.md)이며 그 표는 수정 전 상태의 기록이다.
  권한 매트릭스는 D-040으로 **부분** 확정이다. 메뉴·테이블 조회의 주체는 아직 정하지 않았고
  그 둘은 역할 제한 없이 인증만 요구한다. 주방 집계는 경로를 제거했다.
  구현과 회귀만으로 위험은 종료되지 않는다. BK-R001은 Critical이고 해결 상태는 Open이다.
  기준 ref와 열린 PR은 아래 명령으로 매 세션 직접 확인한다. 여기에 SHA를 고정하지 않는 이유는
  이 문서를 갱신한 PR이 머지되는 순간 고정값이 낡기 때문이다.
  이 문서만 읽고 다음 단계를 임의로 시작하지 않는다.

## 승인과 범위

D-031로 외부 인터넷 접속을 허용하는 방향이 확정됐다. HTTPS·도메인 연결은 검토 중이다.
2026-09-12에 D-034~039를 확정했다. 주방 공용 계정은 **1개로 단일화**하고(D-034, D-032의 3계정 구분을 대체),
인증은 역할별 고정 id/pw와 JWT로 전환하며 리프레시 토큰은 httpOnly 쿠키에 둔다(D-035).
쿠키 인증이 CSRF 위험을 되살리므로 CSRF 면제 제거와 익명 차단·JSON403은 필수 동반 작업이다(D-036).
보존할 과거 주문 데이터가 없어 0019 과거행 정책 문제가 해소됐다(D-037).
배포 대상은 EC2로 확정했고 main=배포·develop=개발로 나눈다(D-038, D-001·D-021 해소).
운영 필수 설정이 없으면 시작을 거부하고 예시 파일만 저장소에 둔다(D-039).
D-040으로 권한 매트릭스가 부분 확정됐고 2026-09-13에 단계3으로 구현했다.
2026-09-14에 D-042가 4A2 설계를 확정했다(저장 방식·다중 기기·수명·401/403).
D-043으로 `SameSite`=Strict 와 리프레시 CSRF 토큰 방어를 정했다. **이 둘은 사용자가 고른 값이 아니라
에이전트 판단이며 뒤집을 수 있다.** 계정 5개→3개 통합은 D-034에서 이미 승인됐고,
이번 4A2 하위 작업으로 구현했다. 이를 다시 사용자 결정 대기로 둔 이전 안내를 정정한다.
남은 정책 항목은 `menus`·`tables` 주체, 자격증명 회수·교체 절차, 반복 로그인 제한 수치다.
실제 id/password 값은 운영 설정에 필요하며 합성 값으로 진행하는 로컬 JWT 구현의 선행 조건이 아니다.
JWT 계정 저장소·발급·갱신과 실제 외부 공개·배포는 아직 구현·실행하지 않았다.

D-029는 SQLite 실행/테스트 지원 제거, PostgreSQL 전용 설정·번호 경로·개발 Compose·필수 CI 전환 지시다.
이슈·브랜치·PR 작업 방식은 유지한다. 사용자 추가 지시로 PR42 리뷰 보완·머지를 완료했다.
후속 다음 단계 진행 지시로 PR44를 최종 head 확인 후 머지했다. 사용자 지시로 PR48·PR46 순서로 머지하고
머지된 작업 브랜치를 정리했다. 4A1 독립 범위였던 오류 보고의 비노출 처리·회귀·문서는 머지됐고
운영 시작 규칙은 확정하지 않았다. 브랜치 삭제는 사용자 지시로만 수행했고 머지되지 않은 브랜치는 남겼다.
D-P07의0020 적용은 완료됐다. 번호 정책·운영 DB 적용은 미정이고,
EC2 배포 대상은 D-038로 확정됐으나 실제 리소스 생성·배포는 여전히 별도 승인이다.
기존 데이터 파일·과거 migration·counter 테이블을 삭제하지 않는다.
[결정 기록](DECISIONS.md), [현재 전환 범위](POSTGRES_ONLY.md), [작업 로그](WORKLOG.md)를 함께 읽는다.

[POSTGRES_TESTING](POSTGRES_TESTING.md)의 새 전용 Compose 생성·명시적 테스트 URL 설정 후 실행한다.

```bash

```

실제 대상 검증 후 check/drift와 프로젝트 전체 테스트를 migration/app 별도 프로세스로 실행한다.
4A1 잔여 구현 당시 검증은 80개(15+65), 모두 PostgreSQL·skip0이었다. 최신 결과는 [WORKLOG](WORKLOG.md)를 따른다. DB 충돌은 자동 삭제하지 않고 오류로 종료한다.
일반 DATABASE_URL·기존 SQLite 파일·개발용 DB를 테스트 대상으로 사용하지 않는다.
테스트가 끝나거나 실패하면 안내의 소유 label 검증·정리 절차를 따른다.
CI도 같은 명령을 사용한다. PG 성공을0019 정책이나 운영 배포 승인으로 확대하지 않는다.

## 모델 설정과 과거 기록

현재 모델은 사용자가 선택한 실행 환경의 설정을 따른다. 문서는 특정 모델 선택을 강제하지 않는다.
대상 모델의 정확한 식별자·도구 지원·파일/명령/DB 접근은 실제 위임 전에 확인한다.
다른 제공자에게 동일한 API 인수나 추론 수준 이름을 추정해 전달하지 않는다.
이 정리는 모델 설정 변경이나 Opus 5 호출·품질 검증이 아니다.

2026-09-06 초기 준비 기록에서는 GPT-6 Astra, 분석 xhigh·구현 high·어려운 문제 max,
Responses API 사용을 안내했다. 당시 준비 브랜치는 chore/astra-modernization-setup이었다.
이는 **과거 세션 설정 기록**이며 현재 모델/API 요구사항이나 시작 브랜치 지시가 아니다.
당시 db.sqlite3 준비와 GitHub 인증 실패도 현재 실행 전제로 사용하지 않는다.

## 작업 절차

1. AGENTS와 README·BASELINE·BLUEPRINT·DECISIONS·WORKLOG를 읽고 과거 관찰과 최신 상태를 구분한다.
2. 승인된 하위 작업 하나의 기준 ref, 소유 파일, 승인 근거, 제외 범위, 인수 기준을 정한다.
3. 변경 규모에 맞게 검증한다. 문서만 변경하면 링크·명령 구문·자리 표시자·렌더·diff를 검사한다.
4. [구현 프롬프트](prompts/03_IMPLEMENT_PHASE.md)는 실제 작업 지시 시 모든 항목을 채운다.
   0020은 적용됐으나0019·번호 정책·운영 적용을 자동 시작하지 않는다.
5. 결과·실행 검사·미실행 이유·남은 관문을 WORKLOG에 기록하고 인계한다.
