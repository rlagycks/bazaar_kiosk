## 화면과 운영 의미

- 식당·포장·전체 모니터링은 기존 URL과 권한을 유지한다. 상단 `내 메뉴`에서 허용된 업무
  화면으로 이동하거나 POST 로그아웃한다. 누적·통계 UI 교체는 UI-05C다.
- 미완료는 접수 오래된 순의 가로 목록이다. 준비 수량이 모두 차도 **출발 확인 전까지 남는다**.
  아래 전체 기간 내역에는 준비 중·출발·취소를 최근 접수순으로 표시하고 50건씩 이동한다.
- 상세에서는 품목별 `− 숫자 +` 준비 수량을 수정하고 한 번에 저장한다. 메뉴·주문 수량·가격·
  결제 편집과 부분 취소는 추가하지 않는다. 취소 내역은 조회만 가능하다.
- **완료 = 모든 음식 준비 후 손님께 서빙 출발**, 전달 완료가 아니다. 확인 대화상자에서
  모든 준비 수량을 주문 수량으로 맞춘다는 사실을 안내하고, 확인하면 수량·상태·출발 시각을
  한 트랜잭션에 저장한다. 준비 체크를 전부 별도로 누를 필요는 없다.
- 준비 중으로 되돌리면 수량은 유지하고 출발 시각을 지운다. 출발 후 준비 수량을 줄여 저장해도
  준비 중으로 돌아간다. 취소 시 출발 시각은 과거 기록으로 남는다. 감사 이벤트도 유지한다.
- 기존 `READY`에는 출발 시각을 추정하지 않고 **기존 완료 · 출발 미확인**으로 표시한다.
  기존 일반 상태 API의 `READY` 처리도 출발 증거를 만들지 않는다. 출발을 명시하려면
  준비 중으로 되돌린 뒤 새 모니터링 출발 동작을 사용한다.
- READY 포장 주문은 기존 번호표를 계속 점유한다. 전달 완료·번호표 반환 정책은 이번 범위에 없다.

## 읽기 계약

`GET /orders/api/snapshot/monitoring?scope=ALL&page=1&since=<opaque-version>`

`HALL`은 식당 권한, `TAKEOUT`은 포장 권한, `ALL`은 둘 다 필요하다. STATS는 이를 우회하지 않는다.
혼합 주문은 기존 규칙대로 식당에 속한다. 모든 필터는 제한·페이지 처리보다 먼저 적용된다.
응답은 기존 snapshot의 `version`, `unchanged`, `cursor`, `orders`, `total`, `count`,
`has_more`, `complete`와 `history`를 담는다. history에는 `orders`, `total`, `page`, `pages`,
`has_previous`, `has_next`가 있다. 주문에 `departed_at`과 `monitor_version`을 추가했다.

미완료 500건 제한은 유지하며 초과 건수를 표시한다. 전체 내역은 고정 50건, page 범위는
1~1,000,000이다. 범위 밖 페이지는 빈 목록과 마지막 유효 페이지로 돌아가는 링크를 표시한다.
이력 페이지 나눔은 정상 응답이므로 `complete`를 낮추지 않는다. 미완료 잘림만 낮춘다.
`unchanged`는 두 배열을 비우고 이전 표시를 유지하며 합계·페이지 정보는 보낸다.

서비스가 직접 소유하는 PostgreSQL REPEATABLE READ 안에서 변경 번호·두 목록·관련 항목을
직렬화한다. 외부 트랜잭션에 중첩되면 거부하며 뷰는 ATOMIC_REQUESTS 대상에서 제외한다.
커서는 DB 세대·실제 권한·표현 버전·요청 범위·이력 페이지에 결속된다. 기존 waiting-only 커서를
재사용할 수 없다. 조회 쿼리는 1건/501건 fixture 비교에서 SELECT 최대 9개를 회귀 상한으로
검사한다. 이는 운영 부하 측정이나 성능 개선 주장이 아니며 10E는 남아 있다.

10D2 `kitchen_live.js` 하나가 SSE·5초 후퇴 폴링·탭 수명·재시도를 계속 관리한다. 새 화면은
이 snapshot만 그린다. 쓰기 응답은 그리지 않고 동일 스케줄러에 다시 읽기를 요청한다.

## 쓰기 계약과 충돌 복구

`PATCH /orders/api/orders/<id>/monitoring`

```json
{"action":"progress","expected_version":"<monitor_version>","items":[{"id":7,"prepared_qty":2}]}
```

`progress`는 **모든 품목**을 정확히 한 번씩 지정한다. `depart`, `reopen`, `cancel`은 items를
생략한다. 알 수 없는 필드·중복/누락 품목·정수가 아닌 수량·주문 수량 초과는 400이다.
모니터 권한과 JWT 디바이스·CSRF 검사는 기존 경계를 따른다. 잠근 주문의 실제 범위를 다시
확인하며 권한 밖은 403, 오래된 버전·취소 후 변경은 409, 없는 주문은 404다.
성공은 최소한의 `id`, `status`만 반환한다.

주문 → 항목 순으로 잠그고 persisted 주문 필드와 품목 id/메뉴/가격/수량/모드의 해시를 비교한다.
동일 화면에서 동시에 저장하면 한쪽만 성공하고 다른 쪽은 최신 내용을 확인해야 한다.
감사 기록·수량·상태·출발 시각·변경 번호는 함께 커밋/롤백한다. 실제 변경이 없는 fresh-version
재시도는 감사 기록·변경 번호를 늘리지 않는다. 성공 전 버전으로 재전송하면 409다.

입력 중 최신 snapshot이 달라지면 입력을 유지하고 저장/출발을 막는다. 빈칸 등 잘못된 입력도
유실하지 않는다. 최신 내용 다시 보기에서 입력 폐기를 확인한다. 응답 유실·서버 거부 후에는
자동으로 다시 쓰지 않고 초안/오류를 유지한 채 snapshot을 읽는다. 닫기·페이지 이동 때 미저장
입력을 확인한다. 새로고침 후 복원은 제공하지 않는다.

## 스키마와 복구

새 마이그레이션 `0030_order_departed_at`은 nullable 출발 시각만 추가한다. 과거 마이그레이션과
과거 주문을 수정하거나 READY를 일괄 변환하지 않는다. 기존 필드·가격·주문 번호는 보존된다.
빈 DB 전체 설치와 0029→0030→0029 경로, 기존 모델의 기존 필드 읽기/쓰기를 검사한다.

이전 앱은 추가 컬럼을 무시하고 실행할 수 있지만 **수량만으로 READY를 만들던 의미는 안전하게
되돌릴 수 없다**. 운영 복구는 쓰기를 중지하고 인증·인가·CSRF·안전한 DOM 보호를 유지한 채
0030을 남기는 정방향 수정을 우선한다. 출발 기록 생성 후 0029로 역행하면 그 기록이 삭제되므로
단순 UI 롤백으로 취급하지 않는다. 운영 마이그레이션·배포는 이번에 실행하지 않았다.
