기존 `/orders/b1-counter/`에 적용했다. PR82의 공통 UI를 기반으로 별도 worktree에서 구현했다.
PR82 머지 후 develop `e61d6ab` 기준으로 통계 변경만 별도 PR로 제출한다. 합병·배포 상태는 최신 WORKLOG와 실제 PR을 확인한다.

## 화면과 집계

- 주문 건수·판매 수량·총 매출·순현금 카드, 현금·거스름돈·식권 수납 내역,
  날짜별 시간대 매출 막대와 수치 표, 메뉴별 판매 표를 배치했다.
- 내 메뉴는 기존 공통 대화상자를 사용한다. 개인 이름, 허용된 업무 링크, CSRF 보호 POST
  로그아웃을 제공하며 서버의 STATS 인가와 JWT 자동 갱신을 유지한다.
- [D-053 집계 계약](REPORTING.md)을 유지한다. 최근 등록 행사일(오늘 이하), 없으면 오늘이 기본이다.
  명시 기간은 양 끝 포함이며 한국 시간 기준이다. 행사 번호 주문만 집계하고 취소·연습은 제외한다.
  매출은 판매 금액, 순현금은 받은 현금−거스름돈이다. 환불 정산이나 실제 금고 잔액이 아니다.
- 과거 혼합 결제의 수단별 금액을 알 수 없으면 기존대로 매출에는 포함하고 수납 내역에서는
  제외한다. 해당 건수·금액을 경고로 표시한다. 수납 합계가 0이면 현금·식권 비율을 모두 0%로 표시한다.
- API의 `hourly[]`에 `date: YYYY-MM-DD`만 추가했다. 기존 TruncHour의 날짜별 그룹·순서·금액과
  쿼리 수는 유지한다. 여러 날의 10시가 별개라는 점을 차트와 표에서 식별할 수 있다.
- API 문자열은 안전한 DOM 텍스트로 렌더링한다. 차트는 CSS로 그리며 외부 폰트·이미지·차트 서비스가 없다.

## 조회와 실패 복구

조회와 기본 행사일 버튼으로 갱신한다. 기존 수동 조회를 유지하며 조회 완료 시각과 자동 갱신 없음도 표시한다.
입력 중인 기간과 **실제로 적용된 결과 기간**을 분리한다.

1. 첫 조회 전에는 숫자를 `—`로 둔다. 성공한 0건 응답만 빈 결과/0원을 표시한다.
2. 통신 실패·잘못된 기간·권한 오류·불완전한 성공 응답에는 이전 성공 결과와 그 기간을 유지한다.
   조회 실패가 0원이라는 뜻이 아님을 알리고, 다시 시도는 실패했던 기간을 재전송한다.
3. 연속 조회에서는 마지막 요청의 결과만 적용한다. 늦게 도착한 성공·실패가 최신 결과를 덮지 않는다.
4. 응답을 기다리는 동안 사용자가 날짜를 편집하면 그 입력을 이전 요청의 날짜로 덮지 않는다.
5. 인증 소멸은 공통 인증 처리로 로그인 화면에 돌려보낸다. 기존 데이터를 새 조회 결과로 표시하지 않는다.

## 검증과 한계

- `node --test scripts/test_stats_ui.cjs`: 13개. 실제 controller의 실패/재시도·응답 역전·날짜 입력
  보존·빈 결과·안전한 텍스트·기간별 차트와 불완전한 응답 거부를 검증한다. CI 전체 Node 98개 통과.
- 격리 PostgreSQL 전체 검사 622개(마이그레이션 27+일반 595) 통과. 날짜 추가의 합계 불변,
  한국 자정 경계, 같은 시각의 서로 다른 날짜, 페이지 권한·회수·출력 이스케이프를 포함한다.
- 브라우저 합성 데이터: 1440×1000/1024×768, 기본 행사일·범위 조회·0건·역전 기간 오류/재시도,
  이전 결과 보존, 권한별 내 메뉴·Escape 초점 복귀, 시간대 수치 표와 문자열 안전성을 확인한다.
  최종 실행 결과와 추가 검증은 WORKLOG에 기록한다.
- 실제 운영 데이터·실기기·음성 스크린리더 인수는 하지 않았다. Django 관리자 자체의 재디자인,
  CSV 내보내기·실시간 통계·새 정산 규칙은 이번 범위가 아니다. 10E 부하와 12 운영 인수도 남아 있다.
