## 확정된 완료 규칙

사용자는 "접수순으로 반영하고 전량 충족 주문은 완료"를 선택한 뒤, 혼합 주문도 품목별로 분리하도록 승인했다.
같은 메뉴의 수량을 `created_at` → 주문 `id` → 품목 `id` 오름차순으로 배분한다. 남은 수량과 배분 대상은 오늘(Asia/Seoul)
접수 주문만이다(D-077). 이전 날짜의 미완료 주문은 오늘 완료 수량을 가져가지 않는다.
대상은 PREPARING 주문의 TAKEOUT 품목이며 순수 포장과 혼합 주문을 모두 포함한다.
선택한 메뉴 수량을 한 트랜잭션에 반영하며, 일부만 처리된 품목의 나머지는 계속 남는다.
결제 금액·주문 수량·교환권 번호는 변경하지 않는다.

| 주문과 동작 | 반영할 품목 | 주문 전체 상태·출발 기록 |
| --- | --- | --- |
| 순수 포장의 일괄 완료 | TAKEOUT만 | 전량 충족하면 READY. `departed_at`을 생성하지 않음 |
| 혼합 주문의 포장 완료가 먼저 | TAKEOUT만 | 식당 수량이 남아 있으면 PREPARING |
| 혼합 주문의 식당 출발이 먼저 | DINE_IN만 전량 준비 | 포장이 남으면 PREPARING, `departed_at`과 `DEPARTED` 감사 이벤트 기록 |
| 혼합 주문의 양쪽 처리 완료 | 양쪽 품목 전량 충족 | READY(식당 `departed_at`은 식당 수량 충족 시 자동 기록, D-076) |

D-076부터 식당 준비 수량을 전부 채우는 `progress`가 곧 식당 출발이다(자동 기록). 식당 `depart`는 혼합 주문의 식당 품목만 채우고,
포장 품목을 대신 완료하지 않는다. 혼합 주문의 식당 출발은 전체 상태가 PREPARING이어도 식당 미완료 목록에서 빠지며,
식당 이력에서 출발·포장 대기를 구분한다. 구형 상태 API·관리자의 직접 READY 변경도 양쪽 완료/출발 조건을 우회하지 못한다.

식당 재개는 준비 수량을 유지하면서 출발 시각을 지운다. 품목 수량을 줄여 재개할 때 포장만 미완료라면
이미 기록된 식당 출발은 유지하고, 식당 품목이 미완료가 되면 출발 시각을 지운다. 취소는 기존 최종 상태 규칙을 따른다.

리뷰 후속 보완 계약은 구형 품목 진행·관리자 편집에도 같은 상태 규칙을 적용하는 것이다. 식당 출발이 기록된 혼합 주문의
모든 수량이 충족되면 `sync_from_items`가 READY로 맞춘다. 순수 포장 READY 주문을 관리자 편집으로 혼합 주문으로 바꾸면,
식당 출발 기록이 없는 경우 수량이 모두 차 있어도 PREPARING으로 되돌린다. 관리자 READY 검증도 저장할 품목 구성과
출발 조건을 확인한다(식당 출발 없이 혼합 주문을 READY로 저장하면 폼 오류). 취소 주문과 순수 식당 주문은
재조정하지 않는다. 순수 식당 주문도 모든 수량이 준비되면 출발·READY가 자동 기록된다(D-076).

식당 모니터의 혼합 주문 카드는 기존처럼 주문 금액·메모를 표시한다(사용자 결정 2026-10-03, 리뷰 M1 보류).

기타 품목은 D-073의 저장된 메뉴 연결을 따른다. 메뉴가 연결된 기타 줄은 해당 메뉴에 합산하고,
연결이 없는 이름은 기존 공백·대소문자 정규화 규칙으로 묶는다. 과거 줄을 현재 메뉴명으로 재매칭하지 않는다.

## 조회와 권한 경계

화면 URL은 `/orders/kitchen/takeout/`, 전용 읽기는 `GET /orders/api/snapshot/takeout?page=1&since=<version>`이다.
TAKEOUT_MONITOR 권한이 필요하며 STATS만으로는 접근할 수 없다. 서버가 B1의 TAKEOUT 품목을 가진 주문을 고른다.
`menus`의 `key`·`name`·`remaining_qty`와 `remaining_total`, 완료용 `completion_version`, `history`를 반환한다.
활성 주방 메뉴는 잔량이 0이어도 포함하며 비활성·기타 품목도 잔량이 있으면 포함한다. 집계에는 기존 주문 대기열의
500건 제한을 적용하지 않는다. 이력은 `created_at`, `id` 내림차순으로 고정 50건, 페이지 범위는 1~1,000,000이다.

포장 이력의 품목·`total_qty`는 TAKEOUT 줄만 대상으로 한다. `status`·`prepared_qty`·`departed_at`·금액은 반환하지 않는다.
식당 `scope=HALL` snapshot은 DINE_IN 줄만 직렬화하고 `hall_completed`·`takeout_pending_qty`로 식당 출발과 포장 잔량을 알린다.
기존 `scope.visible`/`classify`는 **주문 단위로 혼합=식당**을 유지한다. 이 분류를 넓혀 구형 조회·전체 취소 API에
TAKEOUT 권한만으로 혼합 주문 전체 내용을 허용하지 않는다. 구형 품목 진행 API는 잠근 대상 품목의 `service_mode`에 따라
HALL_MONITOR 또는 TAKEOUT_MONITOR를 검사한다. 혼합 주문의 모니터링 `progress`는 식당 품목 전체만 받는다.

읽기는 자체 PostgreSQL REPEATABLE READ 트랜잭션에서 버전·집계·이력을 함께 만든다. `version`은 권한·표현·페이지·DB 세대에
결속된 조회 커서다. `unchanged`이면 메뉴·이력 배열을 비우고 클라이언트는 기존 표시를 유지한다.
SSE와 후퇴 폴링은 기존 `kitchen_live.js` 스케줄러가 담당한다. 포장 변경 감지는 미완료뿐 아니라 0개 메뉴와 전체 기간 이력도
포함해 완료된 과거 주문이나 카탈로그 변경에도 다시 읽는다. 완료 응답으로 화면 수량을 직접 차감하지 않고 snapshot을 재조회한다.

## 일괄 완료 요청과 영속 영수증

`POST /orders/api/takeout/complete`는 TAKEOUT_MONITOR·기존 JWT 디바이스 인증·CSRF 경계를 따른다.
필수 필드는 **`request_id`, `expected_version`, `items`**다. 클라이언트가 새 완료 배치마다 고유한 `request_id`를 만들고,
snapshot의 **`completion_version`**을 `expected_version`으로 보낸다. 조회 커서 `version`과 혼동하지 않는다.

```json
{
  "request_id": "0ab40d81-581c-4d37-9d93-3b6fe2e6b423",
  "expected_version": "<completion_version>",
  "items": [{"key": "menu:7", "quantity": 2}]
}
```

예시의 버전과 메뉴 키는 실제 snapshot 값으로 바꾸며, 새 배치에는 예시 ID를 재사용하지 않는다.
선택이 양수인 메뉴만 보내며 각 `key`는 한 번만 지정한다. 메뉴 연결이 있으면 `menu:<id>`, 미연결 기타는 서버가 제공한
`custom:<hash>` 키를 그대로 쓴다. 요청 ID 누락/형식 오류·빈 선택·중복 키·정수가 아닌 수량·알 수 없는 필드는 400이다.
정상 성공 응답은 200이며 `completed_qty`는 반영 수량, `completed_orders`는 그 배치로 전체 READY가 된 주문 ID다.
혼합 주문의 식당 처리가 남았다면 수량 반영이 성공해도 해당 주문은 `completed_orders`에 들어가지 않는다.
재시도 응답은 저장된 당시 결과이므로 현재 잔량과 이력은 snapshot으로 다시 읽는다.

`TakeoutCompletionRequest`는 고유 요청 ID, 인증된 행위자, 요청 내용 지문, 결과를 DB에 보관하는 완료 영수증이다.
내용 지문에는 `expected_version`과 메뉴 키별 선택 수량이 들어간다. **만료는 없다.** 인증·권한 검사를 통과한 재요청은
저장된 영수증을 먼저 확인하므로, 같은 ID·행위자·내용이면 표시 버전이 오래됐어도 저장된 200 결과를 반환한다.
수량·감사·변경 번호를 다시 쓰지 않는다. 이 계약은 초기의 버전 비교만으로 재전송을 거부하던 설계를 대체한다.

| 요청 조건 | 응답·반영 |
| --- | --- |
| 새 ID·현재 버전·유효한 잔량 | 배치와 영수증을 함께 저장하고 200 |
| 저장된 ID·같은 행위자·같은 내용 | 버전이 오래돼도 저장된 결과로 200, 추가 반영 없음 |
| 저장된 ID·다른 행위자 또는 다른 내용 | 409, 기존 영수증과 주문은 그대로 |
| 서로 다른 ID·같은 표시 버전으로 경합 | 한 요청만 반영해 200, 나머지는 409 |
| 새 ID·오래된 버전 또는 잔량 초과 | 전체 409, 배치와 영수증 모두 미저장 |

서버는 요청 ID를 확보하고 주문 ID 순으로 주문을 잠근 뒤 품목을 잠근다. 새 요청은 DB 세대와 포장 품목의 메뉴 키별
준비 완료 수량 합계 해시를 비교하고 잔량을 확인한다. 이 범위는 사용자 결정(2026-10-03)으로, 새 주문 도착이나
혼합 주문의 식당 진행은 선택 중인 배치를 거부하지 않는다. 같은 포장 수량을 다른 기기가 먼저 완료한 경우만 409다. 하나라도 잔량이 부족하거나 키가 현재 잔량에 없으면 전체를 거부한다.
영수증·준비 수량·주문 상태·감사 기록·변경 번호는 같은 트랜잭션에서 커밋/롤백한다. 실패하거나 롤백된 요청에는
영수증이 남지 않는다. 이미 커밋된 뒤 응답만 유실된 경우에는 영수증이 남아 다음 정확한 재시도를 처리한다.

## 클라이언트의 불명확한 결과 복구

네트워크 오류·응답 유실·5xx로 결과가 불명확하면 **최초 payload와 `request_id`를 그대로 보관**한다.
수량 편집과 새 완료 배치를 잠그고 **`완료 결과 다시 확인`** 버튼으로만 같은 POST를 수동 재시도한다.
이때 `expected_version`도 최초 값을 유지한다. 자동 POST는 하지 않으며, snapshot 갱신만으로 잠금을 풀거나
잔량 변화에서 성공을 추정해 새 ID를 발급하지 않는다. 저장된 결과를 받은 뒤 최신 snapshot으로 화면을 갱신한다.

확정된 400/409 응답은 최신 내용을 검토해 새 배치를 만들 수 있게 한다. 제출 전 서버 버전이 달라진 선택도
최신 내용을 확인해야 한다. 저장 중에는 중복 클릭을 막고, 쓰기 전에 시작한 늦은 읽기 응답이 복구 잠금을 풀지 못하게 한다.
페이지 이동·새로고침·닫기는 미확인 요청이나 선택이 있을 때 `beforeunload`로 보호한다. 요청 보관은 페이지 메모리뿐이며
재로딩 후 복원은 제공하지 않는다. 서버 영수증이 영속적이라는 사실을 브라우저의 요청 복원 기능으로 해석하지 않는다.

## 마이그레이션과 복구

기존 `prepared_qty`·`status`·`departed_at`을 재사용한다. `0033_mixed_departure_event`의 `OrderEvent.kind`
선택지 `DEPARTED` 추가는 유지한다. 혼합 주문은 전체 상태가 바뀌지 않아도 식당 출발 사실과 행위자를 감사에 남긴다.
후속 `0034_takeout_completion_request`는 `TakeoutCompletionRequest` 테이블만 추가한다. 기존 주문 데이터 쓰기나
주문 컬럼 변경·백필은 없다. 운영 마이그레이션은 이번에 실행하지 않는다.

구버전 식당 출발 코드는 혼합 주문의 포장 수량까지 채울 수 있어 이 데이터에서 안전한 롤백 대상이 아니다.
또한 **0034 사용 후 역이행은 완료 영수증을 지워 중복 반영을 허용할 수 있으므로 정방향 수정으로 복구한다.**
쓰기를 중지하고 인증·인가·CSRF·안전한 DOM 보호, 출발·감사·완료 영수증을 보존한다. 영수증 삭제나 만료 처리를 복구 수단으로
사용하지 않는다. 0033 choices만 되돌려도 새 완료 규칙은 복구되지 않는다. 기존 D-069·D-073의 데이터 보존 제약도 적용한다.

다음은 검증 대상이며 통과 선언이 아니다. 실행 결과와 미확인 범위는 총괄 담당자가 [WORKLOG](WORKLOG.md)에 기록한다.

  영수증 원자성·동일 요청 200 재생·ID 재사용 충돌·서로 다른 ID의 버전 경합·실패 시 영수증 미저장·혼합 주문 완료 순서·
