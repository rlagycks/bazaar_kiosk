# 프롬프트 01 — 증거 우선 레거시 분석

모델 공통 실행 계약과 과거 설정 구분은 [세션 안내](../SESSION_SETUP.md)를 따릅니다.
모델과 도구 설정은 실제 실행 환경에서 확인하며 다른 제공자의 인수를 그대로 사용하지 않습니다.

준비된 저장소에서 새 작업을 열고 아래 프롬프트를 복사해 넣으세요. 이 작업은
분석 작업입니다. 현대화 보고서를 만들거나 업데이트할 수 있지만 애플리케이션
수정 사항을 구현해서는 안 됩니다.

```text
이 Bazaar Kiosk 저장소를 충분히 깊이 분석하여 현대화 계획을 안전하고 실행
가능하게 만드세요. 저장소의 AGENTS.md를 작업 규약으로 삼고, 결론을 내리기 전에
docs/modernization/README.md, BASELINE.md, BLUEPRINT.md, GIT_RECOVERY.md,
DECISIONS.md, WORKLOG.md를 읽으세요.

이 단계에서는 증거를 우선하며 분석만 수행합니다. 프로덕션 코드, 과거 마이그레이션,
의존성, CI, 원격 Git ref, GitHub 설정, 인프라 또는 프로덕션 데이터를 수정하지
마세요. 읽기 전용 명령을 실행하고 무시 목록에 포함된 로컬 환경/테스트 데이터베이스를
만들 수 있습니다. 내가 명시적으로 범위를 확장하지 않는 한 다음 분석 산출물에만
쓸 수 있습니다.

- docs/modernization/ANALYSIS_REPORT.md
- docs/modernization/RISK_REGISTER.md
- docs/modernization/BASELINE.md의 증거에 근거한 수정
- docs/modernization/DECISIONS.md의 대기 중(pending) 또는 제안됨(proposed) 항목. 사용자가
  해당 결정을 명시적으로 제공하지 않았다면 결정 상태를 승인됨(accepted)으로 표시하지
  마세요.
- docs/modernization/WORKLOG.md의 새 항목

일상적인 세부 사항은 저장소에서 추론하고 자율적으로 계속 진행하세요. 증거 수집에
필요하지 않은 질문을 하려고 멈추지 마세요. 해결되지 않은 제품 관련 질문은 추측하지
말고 보고서와 DECISIONS.md의 제안됨/대기 중(proposed/pending) 항목에 기록하세요. 접근 권한이나
모호성이 모든 유용한 분석을 막는 경우, 또는 다음 작업이 파괴적이거나 되돌릴 수 없거나
외부에 영향을 주거나 이 승인된 범위를 벗어나는 경우에만 나에게 직접 질문하세요.

추적 중인 소스 전체와 관련 Git 기록을 조사하세요. 코드, 워크플로 및 설정을 근거로
실제 런타임과 배포 가정을 확립하세요. Python 3.12에서 기존 검사를 실행한 다음,
의존성을 추가하지 말고 사용 가능한 도구로 집중적인 정적 검사를 수행하세요. SQLite에서
관찰한 내용과 PostgreSQL 또는 Supabase가 있어야 확인할 수 있는 주장을 구분하세요.
로컬에서 검증할 수 없는 프로덕션 동작을 사실처럼 주장하지 마세요.

다음의 독립적인 작업 흐름을 다루세요.

1. 제품 및 도메인 동작: 운영자 여정, 주문 수명 주기, 테이블/포장 의미 체계, 가격 책정,
   현금/식권 결제, 취소, 통계 및 일자 경계.
2. 보안: 인증, 경로 및 메서드별 인가, CSRF, 세션 정책, 기본 자격 증명, 입력 검증,
   XSS/안전하지 않은 DOM 렌더링, 비밀 정보, 서드 파티 스크립트, Django 배포 설정 및
   Supabase RLS 가정.
3. 데이터 및 동시성: 트랜잭션 경계, 중복 제출, 멱등성, 상태 경합, 합계 무결성, 제약 조건,
   마이그레이션 안전성, PostgreSQL 시퀀스 동작, 자정 전환, 재시도 및 백엔드 간 동등성.
4. 성능 및 실시간 처리: 쿼리 형태와 쿼리 수 관련 위험, 인덱스, 페이로드 크기, 캐시와
   무효화, 폴링, 재연결/중복 제거, 다중 워커 동작 및 측정에 필요한 구체적인 워크로드.
   벤치마크나 계획상의 근거 없이 코드가 더 빨라졌다고 판단하지 마세요.
5. 유지보수성 및 프런트엔드: 모듈 책임, 사용하지 않거나 중복된 코드, 인라인
   JavaScript/CSS, 오류 계약, 접근성, 터치 기반 작업 흐름, 브라우저 지원 및 테스트
   접점.
6. 배포 및 운영: 의존성 재현성, CI 범위, 지원 버전, 환경 검증, 로깅/메트릭, 상태 확인,
   백업 및 복원, 릴리스/롤백 및 장애 대응 런북.
7. Git: 그래프 문제 분류, 브랜치별 고유 작업, 콘텐츠 수준의 비밀 정보 위험 및
   비파괴적인 정리 방안. ref나 저장소 설정을 변경하지 마세요.

협업 도구를 사용할 수 있다면 실제로 독립적인 작업 흐름을 병렬로 위임하세요. 각
에이전트에 구체적인 질문을 주고, 중복 분석을 피하며, 통합 책임자는 한 명으로
유지하세요. 메시지와 보고서는 사람이 알아볼 수 있어야 합니다.

각 발견 사항에 다음을 제공하세요.

- 안정적인 ID와 심각도(치명적/높음/중간/낮음, Critical/High/Medium/Low)
- 상태(재현됨/코드로 뒷받침됨/프로덕션 의존/가설,
  Reproduced/Code-supported/Production-dependent/Hypothesis)
- 정확한 파일 및 줄 증거 또는 명령/재현 절차
- 영향을 받는 운영자/비즈니스 불변 조건
- 현실적인 실패 또는 악용 시나리오
- 가장 작고 안전한 개선 방향, 의존성 및 회귀 테스트
- 확신 수준과 남아 있는 미확인 사항

외관상의 코드 품질이 아니라 위험과 의존성을 기준으로 발견 사항의 우선순위를
정하세요. 기존 BASELINE.md의 오탐이나 수정 사항을 명시적으로 밝히세요. 경로 및 권한
매트릭스, 데이터 흐름 설명, 마이그레이션/번호 부여 분석, 테스트 공백 지도, 성능 측정
계획 및 Git 권고안을 포함하세요.

ANALYSIS_REPORT.md의 마지막에는 증거와 장단점을 제시하고 점진적 현대화, 부분 교체
또는 완전한 v2 재구축 중 하나를 선택한, 의사 결정에 바로 사용할 수 있는 권고안을
넣어야 합니다. RISK_REGISTER.md는 심각도, 의존성, 담당자 및 대상 블루프린트 단계별로
정렬할 수 있어야 합니다. 이 단계에서는 수정 사항을 구현하지 마세요.

완료하기 전에 Markdown 링크를 검증하고 git diff --check를 실행하세요. 실행한 명령,
실행할 수 없었던 검사, 작성한 파일, 수정한 가정 및 다음에 사용할 정확한 프롬프트를
WORKLOG에 업데이트하세요. 최종 응답에서는 권고안을 먼저 제시한 뒤 핵심 증거, 생성한
파일, 실행한 검사 및 나에게 필요한 결정을 요약하세요.
```
